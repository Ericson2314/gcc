# THE FOUR REMAINING LANGUAGE LISTS, AND THE THREE BACK ENDS THAT DID NOT ASSEMBLE

Worktree `agent-a94d141d788a6b54f`.  Answers the two-half task: convert
`d_target_objs`, `rust_target_objs`, `jit_target_objs` and
`fortran_target_objs` as `cxx_target_objs` was converted; and diagnose, by
name, the three back ends that compile 7/7 and assemble 0/7 or 1/7.

**Headline, in the order it had to happen:**

1. **The brief's prescribed fix for Half 1 was wrong and is contradicted here.**
   `MT_<LANG>_OBJS_<base> = $(MT_C_OBJS_<base>)` **by reference** is right for
   C++ and wrong for the other three, because `<cpu>-c.cc` serves both C and
   C++ while `<cpu>-d.cc`, `<cpu>-rust.cc` and `<cpu>-jit.cc` are different
   translation units defining different symbols.  Written as briefed it would
   have put the C-family object into the D link, built **no `<cpu>-d.o` for
   anybody**, and left the entire defect in place while looking converted.
2. **`fortran` is cleaner than the brief says, and the difference matters.**
   Not "darwin and vms, neither in the 47-base set" -- `darwin-f.o` and
   `vms-f.o` are the **only** two objects any `config.gcc` line puts in that
   variable, and **neither is a back end's own object anywhere in the tree**:
   there is no `config/<cpu>/<cpu>-f.cc` and no back end has cpu_type `vms`.
   So the list is empty for every base on **any** base set.
3. **`bpf` is NOT defective and the "1 of 7" figure is the harness.**
   Corrected below with two independent measurements.
4. **`hppa64` and `microblaze` are real, and each is one named macro** --
   `ASM_OUTPUT_LABELREF` and `ASM_GENERATE_INTERNAL_LABEL`, both the primary's
   for all 47 bases.  Both fixed.
5. The `-DMT_BASE` that the fix then needed **pulled the primary's `tm.h` into
   the very object that exists to capture another base's answers** -- loudly,
   and it is the silent form of that which the branch is about.

## 1. HALF 1 -- THE FOUR LISTS

Population, measured from `config.gcc` and the tree, not assumed:

| list | back-end-owned objects | how loud it was |
|---|---|---|
| `d_target_objs` | **10** back ends have `config/<cpu>/<cpu>-d.cc` (9 of them in the 47-base set; loongarch is not) | **SILENT for 4 of 10** |
| `rust_target_objs` | **1** -- i386 | loud (already had the witness) |
| `jit_target_objs` | **1** -- i386 | **LOUD** |
| `fortran_target_objs` | **0**, tree-wide | clean, and clean because the population is empty |

**Why `jit` was loud and `d` was not, which is the whole finding.**
`config/i386/t-i386:54` builds `i386-jit.o` with a bare `$(COMPILE)`, so it
gets no `-DMT_BASE`; `i386-jit.cc` includes `multi-target-base.h`, whose
witness fires naming both the flag and the file.  `d` fails **identically** and
said nothing for four of its ten back ends, because `aarch64-d.cc`,
`loongarch-d.cc`, `pa-d.cc` and `riscv-d.cc` carried no `multi-target-base.h`
at all -- they reach the primary's `tm.h` transitively through `target.h` and
compile cleanly for every base.  Those four now carry the witness.

Converted in the same channel as C and C++: recorded per target in the
manifest, unioned per back end over **every** record (`pa` proves the need --
four separate hpux/linux/openbsd records each append `pa-d.o`), compiled once
per base into `mt-<base>/` with that base's `-DMT_BASE` and renames, and
filtered out of the shared `@<lang>_target_objs@` so the two copies cannot both
reach a link.

The brief asks for this distinction and it is not the one the brief expected.

* **VERIFIED BY A BUILD, all eleven per-base language objects, 0 `error:`, each
  with its own `-DMT_BASE=<base>-inc`:**

  ```
  mt-i386/i386-d.o     mt-aarch64/aarch64-d.o  mt-pa/pa-d.o    mt-riscv/riscv-d.o
  mt-mips/mips-d.o     mt-rs6000/rs6000-d.o    mt-s390/s390-d.o
  ```

  **No GDC and no cargo were needed for this**, and that is worth saying
  because the brief assumed otherwise: compiling a back end's `<cpu>-d.cc`
  against that base's headers is a `make <object>` in the configured build dir.

  them.

* **OWED, and named rather than implied:** no `d21`, `cc1jit`, `f951` or
  `rust1` was LINKED with these lists, so "the right objects reach the right
  link" is checked at the make-variable level and not observed at a link.  `d`
  needs GDC and `rust` needs cargo, neither on this host; `jit` needs
  `--enable-host-shared`, which is a build-configuration change I did not make.

### The residual this does NOT fix, stated because it will read as done

Converting the list gives each back end its own `<cpu>-d.o`.  It does **not**
make the D front end consult them.  `targetdm` is defined **once**, in
`config/default-d.cc:28`, as `TARGETDM_INITIALIZER` -- built from the macros in
`tm_d.h`, which is generated from `@tm_d_include_list@`, i.e. **the primary
target's `tm_d_file`**.  So a `d21` holding nine back ends' `<cpu>-d.o` still
calls i386's `ix86_d_target_versions` for all of them.

The same is true of `tm_rust.h`/`targetrustm` and `tm_jit.h`/`targetjitm`.

This is the `targetm_c_ops` shape exactly, and the fix is the same shape: a
`target-d-ops-<cpu>.o` per base plus a `target-d-ops-select.o` registry keyed
by base.  **Building the objects is the necessary first half of that and is
what landed here.**  It is a design question in the sense of PRINCIPLES 2b --
it decides where `targetdm` lives -- and it is handed back measured rather than
resolved.

### `bpf` -- NOT A DEFECT.  The harness assembled without the target's `ASM_SPEC`.

`a76a331dcb554f700-corpus.sh` invokes `<triple>-as` **with no flags**.  That is
right for most targets and wrong for any target whose `ASM_SPEC` carries
something the assembler needs in order to *parse* what the compiler emits.
`config/bpf/bpf.h:28` passes `-mdialect=pseudoc` by default; without it GNU as
reads pseudo-C output in the `normal` dialect and says
`unrecognized instruction 'w0 += 1'`.

Two independent measurements, both **7/7**:

```
same .s, as -mdialect=pseudoc                    7/7   (-asflags.sh)
recompiled and assembled THROUGH the driver      7/7   (-drivas.sh)
```

and bpf's `ASM_SPEC` line is present and correct in its per-target `specs`
file, so the driver applies it on the path a real user takes.  **The "bpf
assembles 1 of 7" figure was never a statement about the compiler.**

`-drivas.sh` also records its own near-miss: with `-B$B/gcc/` before the
assembler directory the driver found the **host** `as` and reported
`as: unrecognized option '-EL'` -- an x86 assembler complaining about a bpf
flag.  Our directory must come first.

### `hppa64` -- `ASM_OUTPUT_LABELREF`, the floor-fires class

One shared consumer, `assemble_name_raw` (`varasm.cc:3011`), reached by every
label, `.globl`, `.type` and `.size`.  `defaults.h:197` floors the macro and
the primary's chain does not define it, so **the floor fires for all 47**.  pa
is a dissenter: it marks function symbols internally with a leading `@`
(`FUNCTION_NAME_P`) and `pa.h:1096` strips it back off.  Nothing stripped it:

```
        .globl @f
        .type  @f, @function
@f:
```

`Error: expected symbol name`, all seven inputs.

### `microblaze` -- `ASM_GENERATE_INTERNAL_LABEL`, one label with two authorities

There is **no `defaults.h` floor for this macro at all**: 37 headers under
`config/` define it and **122** shared call sites read the primary's,
`i386/att.h:86`, i.e. `.L`.  microblaze spells it `$L` (`microblaze.h:679`).
Its own `ASM_DECLARE_FUNCTION_SIZE` is compiled in a per-base object and
expands microblaze's macro, while the label **definition** goes through shared
`default_internal_label` -- so the output carries both spellings of one label:

```
.Lfe1:                          <- defined by shared code, primary's spelling
        .size   f,$Lfe1-f       <- referenced by microblaze's own macro
```

`Error: .size expression for f does not evaluate to a constant`, all seven.
Nothing is missing; one name means two things and links cleanly.

Both are converted in the existing `target_asm_ops` channel, exactly as
`ASM_OUTPUT_ALIGN` was, and the second needs **no edit at any of its 122 call
sites** because one `#undef`/`#define` in `multi-target-macros.h` covers them.
Swept before redirecting: every use outside `config/` is a statement and none
is on a `#if` line.

Both selectors fail **by name** when no base is selected, and for
`generate_internal_label` that arm matters more than anywhere else in the file:
the pre-selection default is the primary's table, and `.L...` is accepted by
**every** ELF assembler, so a silent fallback would emit assembly that
assembles everywhere and is wrong on the twenty-odd back ends that spell
internal labels differently.

## 2b. THE THREE MORE BACK ENDS THE SAME FIX CORRECTED, WHICH NO ASSEMBLE ARM COULD SEE

**This is the m68k `%I` finding arriving again, and it is the strongest result
on this board.**  The both-sided arm shows 49 differing pairs over ten targets.
Twenty-eight are label spellings; the other twenty-one are these, and every one
of them was **assembling cleanly at 7/7 before and after**:

| back end | before | after | why the "before" was wrong |
|---|---|---|---|
| `pdp11` | `_gi`, `jsr pc,cb`, `__divsi3` | `_gi`, `jsr pc,_cb`, `___divsi3` | `USER_LABEL_PREFIX "_"` (`pdp11.h:548`), applied by `pdp11_output_labelref`.  Every global symbol was missing its underscore. |
| `bfin` | `.global f`, `call __divsi3` | `.global _f`, `call ___divsi3` | `bfin.h:1014` hardcodes `"_%s"`.  Same shape. |
| `msp430` | `CALL #__mulsi3`, `#__adddf3` | `CALL #__mspabi_mpyl`, `#__mspabi_addd` | `msp430_output_labelref` maps GCC helper names to the **TI ABI** names through `helper_function_name_mappings`.  msp430 was calling runtime functions **that do not exist in its runtime**. |
| `alpha` | `.LFB0` | `$LFB0` | alpha's own `ASM_GENERATE_INTERNAL_LABEL`. |
| `ia64` | `.global f` | `.global f#` | ia64 requires the `#` suffix on symbol references. |
| `mmix` | `STTU $0,@si` | `STTU $0,si` | mmix strips its own marker, exactly as pa does. |

`__mulsi3` and an unprefixed `_f` **assemble perfectly** -- they are undefined
symbols, and `as` has no opinion.  A compile-and-assemble board scores all six
of those rows as a pass in both columns.  The only instrument that could see it
was a byte comparison against the same compiler without the fix.

`scratchpad/a94d141d788a6b54f-whydiff.sh` is what makes a nonzero DIFFER column
readable: for a change like this one **"0 DIFFER" would have meant the
conversion was DEAD**, so a bare count proves nothing in either direction.  It
classifies each differing pair as LABELS-ONLY or OTHER and prints the OTHER
diffs, and it exits 9 if it examined no differing pair at all.  Its label test
is deliberately over-eager, so it can only move a row from LABELS-ONLY to
OTHER -- the direction that costs reading rather than the direction that hides
something.

## 2c. A LEAK THIS FIX ROUTES AROUND WITHOUT CLOSING -- named, not fixed

`toplev.cc:1449` is `user_label_prefix = USER_LABEL_PREFIX;` in a **shared**
TU, so the runtime variable holds the **primary's** answer (`""`) for all 47
bases.  **39 headers under `config/` define that macro and 14 of them say
`"_"`** -- arm, bfin, cris, epiphany, h8300, m68k, mn10300, pdp11, rl78, rx,
sh, sparc, v850, vax (plus darwin and i386/bsd, not in this set).

The back ends above are fixed **only because each has its own
`ASM_OUTPUT_LABELREF`** that spells the underscore itself.  A back end that
wants `"_"` and relies on `defaults.h`'s generic body still reads the shared
variable and still gets `""`.  This is a separate conversion
(`USER_LABEL_PREFIX` into the per-base table, or `user_label_prefix` into
`targetm_cdata`) and it is **not done here**.

## 3. THE THING THE FIX ITSELF THEN FOUND

`target-asm-ops.cc` was deliberately minimal -- strings out of `tm.h`.  The two
wrappers expand whole bodies out of 37 back-end headers, and:

* **it had no `-DMT_BASE`**, so `target.h:57`'s `MT_HEADER (tm.h)` degraded to
  a bare `"tm.h"` -- the build root's shared copy, i386's whole chain under a
  target-neutral name.  `target-asm-ops-alpha.o` failed with
  `ix86_asm_output_labelref was not declared`,
  `conflicting declaration typedef struct ix86_args CUMULATIVE_ARGS` and
  `multiple definition of enum opt_code`: **i386's headers arriving underneath
  alpha's, in the object whose entire purpose is to capture alpha's answers.**
* **`rtl.h` must precede `TM_P_H_FILE`**, and this is the sharper one.  A back
  end's `<cpu>-protos.h` wraps most of itself in `#ifdef RTX_CODE`.  Included
  after `tm_p.h` the header was found, opened, parsed and **contributed
  nothing** -- present and empty, which is the same object as absent.  Of 47
  bases exactly **one** was positioned to notice: i386, because
  `i386-protos.h:205` is inside that guard while alpha's equivalent is not.

`scratchpad/a94d141d788a6b54f-taoptry.sh` compiles this one file per base in
seconds instead of forty minutes per attempt.  It reads the compile command out
of the build dir's own `all-gcc.log`, takes the source from the live worktree,
and carries the mandatory negative control (an undeclared identifier the
compiler must NAME -- "exited 0" and "error file non-empty" both pass in the
broken case).  Final reading: **ok=47 fail=0, negative control fired.**

Two secondary defects it had to solve first, both recorded in it: a **failed**
build's log holds compile lines only for the bases `make` reached before it
died, so "the bases in the log" is a population chosen by the bug (it
substitutes into one base's line as a TEMPLATE and asserts the template's name
no longer survives -- an assert that immediately fired on a `.deps/*.TPo`).

## 4. THE NULL-RESULT ARM

*A back end that compiles 7/7 and emits wrong assembly, and one that compiles
7/7 and emits right assembly, differ only if something assembles it.*

That is the whole board in one sentence, and it is discharged three ways:

* the assembler is asserted to **execute** before any verdict (§0), because a
  broken assembler and bad assembly are the same rc;
* the corpus is assembled **through the driver** as well as directly, because
  the harness's own missing `ASM_SPEC` and a compiler defect are the same rc --
  which is how bpf's figure was corrected;
* `taoptry.sh` refuses to score unless a deliberately broken copy produced a
  **named** diagnostic, because a missing compiler and a clean sweep are the
  same empty log.
