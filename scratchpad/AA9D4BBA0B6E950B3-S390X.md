### A NOTE THE NEXT CONVERSION SHOULD COPY: the redirect is half the fix

`#ifdef SELECT_CC_MODE` guards three shared blocks.  The primary defines the
macro, so those blocks were compiled **IN** for all 47 back ends — including
the **27** that define no `SELECT_CC_MODE` and for which upstream compiles them
**OUT**.  A `#undef`/`#define` redirect leaves the name defined and changes
none of that.  The guards had to become `if (mt_has_select_cc_mode ())`.

This is the shape the brief warned about from the aarch64 CFI loss: *ask what
the primary's `tm.h` expands the macro to, and ask separately which side each
conditional lands on.*  They are two questions.

## 3. CAUSE 2 — `return_address_pointer_rtx` (`eadb28e565a`)

The leaked-**absence** shape.  Five back ends define
`RETURN_ADDRESS_POINTER_REGNUM` (`s390` 35, `sh`, `h8300`, `iq2000`,
`microblaze`) and i386 does not, so all four shared `#ifdef` readers were FALSE
for all 47.  `emit-rtl.cc:6355` therefore never ran and
`return_address_pointer_rtx` stayed **NULL for every target**;
`s390_va_start` dereferences it through `make_tree`.

Both-sided, with a non-varargs control so "s390x fails" cannot be confused with
"this build dir compiles nothing" (`agent-aa9d4bba0b6e950b3-vararg.sh`):

```
x86_64     control ok    vararg ok, 979 bytes
aarch64    control ok    vararg ok, 1276 bytes
riscv64    control ok    vararg ok, 775 bytes
s390x      control ok    vararg rc=4 SIGSEGV in make_tree
```

The other three readers (`emit-rtl.cc:859`, `varasm.cc:1577`, `stmt.cc:238`)
are the quiet half and are why this is a table field rather than a repair at
the crash site.

**Upstream bug found on the way, deliberately NOT fixed here:**
`read-rtl-function.cc:1431` guards its branch with
`#ifdef return_ADDRESS_POINTER_REGNUM` — lowercase `return_`.  That identifier
does not exist, so the branch is dead upstream too, on every target that has a
return address pointer.  Recorded at the field's declaration in
`target-frame.h`.  One for `UPSTREAM-BUGS.md`.

## 4. CAUSE 3 — `la` with a negative displacement.  **31,864 -> 0.**

**IT IS CAUSE 2 IN DISGUISE, ISOLATED AGAINST THE TWO BUILD DIRS THAT SEPARATE
THE FIXES:**

```
                      six-line function, -O2        assembles?
before (no fixes)     la   %r15,-672(%r15)          NO
-after (CC fix ONLY)  la   %r15,-672(%r15)          NO      <- CC fix is not it
-both (both fixes)    aghi %r15,-672                YES, ELF64 IBM S/390
stock                 aghi %r15,-672                -- identical to `-both'
```

and in the full runs, `operand out of range` in the s390x log goes
**31,864 -> 0**, with a non-vacuity control (`Executing on host` 67,925 vs
67,806) proving both ~100 MB logs were read.

### The mechanism, and it vindicates fixing all four readers

`s390.h:659`'s `ELIMINABLE_REGS` names `RETURN_ADDRESS_POINTER_REGNUM` **twice**,
and `s390_decompose_address` (`s390.cc:3371`) decides whether a displacement may
be range-checked yet **by rtx IDENTITY**:

```c
if (lra_in_progress
    || (base != arg_pointer_rtx
        && base != return_address_pointer_rtx      <- NULL, for all 47
        && base != frame_pointer_rtx
        && base != virtual_stack_vars_rtx ...))
  if (!DISP_IN_RANGE (offset))
```

With `return_address_pointer_rtx` NULL, and with `emit-rtl.cc:859` no longer
handing back the canonical RAP rtx, an address based on the return address
pointer compares unequal to every entry in that list.  s390 therefore
classified RAP-based addresses as ordinary ones, and the frame offsets that
elimination was going to rewrite were judged against the wrong branch.

**`emit-rtl.cc:859` is the site that did it, and I had described it in the
commit as the QUIET half — "a second, non-identical `REG` can be made for the
same register".**  That is exactly what happened, and it was worth 31,864
assembler errors rather than the cosmetic risk the phrasing implies.  The
commit's own reason for converting all four readers instead of only the
crash site is now measured rather than argued: **a fix at
`s390_va_start` alone would have stopped 683 segfaults and left 31,864
assembler errors standing.**

### What is still true from the first diagnosis, and worth keeping

- The default `-march` for s390x is `PROCESSOR_2064_Z900` and **the specs-config
  names no `-march` at all**.  Stock has the same default and emits
  `.machine "z900"`; the multi-target build emits **no `.machine` and no
  `.machinemode`**, before or after.  That is a real and still-open divergence
  — same family as the aarch64 `.arch` loss — it is simply not what was
  breaking the assembly.
- The hypothesis that this was an `s390_arch_flags` / `TARGET_LONG_DISPLACEMENT`
  option-state leak was **wrong**.  It was rtx identity, not option state.  The
  evidence that pointed at option state — `-march=z13` fixes it, `-march=z900`
  does not — was real and had a different explanation: z13 has long
  displacement, so `lay` is legal and the misclassified address happens to
  survive.

## 4b. THE ORIGINAL §4, KEPT VERBATIM — and the inference that was wrong

Kept rather than rewritten, because the reasoning below is the kind an agent
will reproduce, and every measurement in it is correct.  **Only the conclusion
drawn from them is false**, and it is worth seeing why.

The inference was: *this reproduces on the unfixed build from a function
containing no CC comparison and no varargs, therefore it is independent of the
other two causes.*  Every clause is true and the "therefore" does not follow.
"Cause A's symptom does not need cause B's trigger" says nothing about whether
they share a ROOT — and here `return_address_pointer_rtx` being NULL has two
symptoms with nothing in common on the surface: a SIGSEGV in `make_tree` on
varargs code, and a mis-classified address in a function with no varargs at all.

**The test that settles independence is not a reproducer, it is a BUILD.**
`-after` (the CC fix alone) existed the whole time and answered it in one
command.  Generalise: when you file a cause as independent, name the build dir
in which the other fixes are present and it still fires.

**This is s390x's largest cause by raw count and it is not an ICE, so no ICE
census on this branch has ever named it.**  Six-line reproducer, and it
reproduces on the **UNFIXED** build:

```c
int sink (char *);
int f (void) { char buf[512]; return sink (buf); }
```

```
multi-target, -O2            la   %r15,-672(%r15)     <- no assembler accepts this
multi-target, -O2 -march=z900 la  %r15,-672(%r15)     <- still wrong
multi-target, -O2 -march=z13  lay %r15,-672(%r15)     <- correct
stock,        -O2            aghi %r15,-672           <- correct
```

`la` is RX-format: its displacement is an **unsigned** 12-bit field, 0..4095,
on every s390 model.  A negative one is not a bad choice, it is not an
instruction.

### What is measured

- **31,864 `operand out of range` assembler errors** in the previous 47-base
  board's s390x log; **0** in the stock s390x log.  Both logs are preserved
  and were re-read here, not quoted.
- **The default `-march` is the SAME on both sides, and that sub-hypothesis is
  DEAD.**  My first theory was that no `-march` reaches cc1 because
  `gcc/configure.ac` is host-only now and nothing put the target's default
  arch into `target-specs`.  The specs-config indeed names no `-march` for
  s390 — but `s390_option_override_internal` defaults to
  `PROCESSOR_2064_Z900`, and **stock emits `.machine "z900"` and gets it
  right anyway.**  Same arch, different instruction.  The default-`-march`
  question is real and separate; it is not this bug.
- **Passing `-march=z900` explicitly does not fix it.**  So it is not that the
  arch is unset: told z900 outright, the multi-target compiler still forms a
  negative displacement and prints `la`.  `TARGET_LONG_DISPLACEMENT` is
  `(s390_arch_flags & PF_LONG_DISPLACEMENT)`, i.e.
  `global_options.x_s390_arch_flags` — **option state**, which PRINCIPLES
  records `nm` is blind to by construction.  Read the value in the running
  `cc1`; do not sweep for symbols.
- **The multi-target build emits NO `.machine` and NO `.machinemode` at all**,
  where stock emits both.  That is a second, probably related, missing
  per-function/per-file directive — the same family as the aarch64
  `ASM_DECLARE_FUNCTION_NAME` / `.arch` loss PRINCIPLES already records, which
  was worth 620 results there.

### The open question, stated as a question

Two authorities appear to disagree about `TARGET_LONG_DISPLACEMENT` *within one
compilation*: something forms the address as though long displacement exists
while the arch is z900.  Whether that is `s390_option_override_internal`
writing a `gcc_options` that the bare `s390_arch_flags` read does not see, or
an insn-alternative/attribute question, is **not established here** and the
two want different fixes.  Start by reading `s390_arch_flags` in the running
`cc1` under both `-march` values.

## 6a. TWO PROCESS FAILURES OF MY OWN, REPORTED BECAUSE THEY ARE CHEAP TO REPEAT

**1. I EDITED A SCRIPT AN IN-FLIGHT RUN WAS EXECUTING.**  PRINCIPLES 5 names
this exactly — `sh` reads a script by BYTE OFFSET, so inserting lines above the
current position shifts every later byte and the shell can resume mid-statement,
executing a fragment that never existed in any version of the file.  I added a
ten-line comment block to `agent-aa9d4bba0b6e950b3-check.sh` while
`sh check.sh before` was running it (the parent was blocked in `mtcheck.sh` and
would have resumed afterwards at the shifted offset).  I killed the run
immediately rather than letting it resume, so no fragment executed, and
re-checked the file with `sh -n`.  **The rule is not "avoid editing harnesses",
it is `pgrep -af <script>` BEFORE the edit**, and I did not run it.

**2. `MT_MAKEFLAGS` UNSET MEANS `-j1`, AND NOTHING SAYS SO.**  `mtcheck.sh`
passes `${MT_MAKEFLAGS:-}` straight to `make check-gcc`.  My first BEFORE run
reached **15,145 of an expected 170,106** `.sum` lines in fifty minutes — about
nine hours for one arm, eighteen for the pair — and there is no diagnostic
anywhere that says the run is serial; it just looks like a slow machine.  Every
board on this branch was taken under `-j` (PRINCIPLES' note that ERRLIN scales
with `-j` is only meaningful if it was used), so the default is a trap for
anyone who copies the invocation without the variable.  `check.sh` now defaults
it to `-j8` and says why.
