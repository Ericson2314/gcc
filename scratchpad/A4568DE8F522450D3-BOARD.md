## 1. WHAT WAS FIXED — ONE BRACKET, TWO BACK ENDS, AND A DEAD `#ifdef`

### 1a. `ASM_DECLARE_FUNCTION_SIZE` — the pop half of a half-converted family

`varasm.cc:2254` spelled `#ifdef ASM_DECLARE_FUNCTION_SIZE`, so it was
answered by whichever base compiled `varasm.cc`. i386 defines no such macro,
so all 47 bases took `elfos.h:397`'s generic `.size` — right for most of the
15 definers, wrong for those whose macro is not about `.size` at all.

**riscv is the sharp case, and it is the board's own "a converted NAME does
not mean a converted FAMILY" lesson recurring three lines away in the same
file.** `riscv.h:1160` `ASM_DECLARE_FUNCTION_NAME` **is converted**; it emits

```
.option push
.option arch, <isa>
```

for any function carrying `#pragma GCC target`, `target(...)` or `norelax`.
`riscv.h:1164` `ASM_DECLARE_FUNCTION_SIZE` — the matching `.option pop` — was
**not**. So the push was emitted and the pop never was: **one bracket,
answered by two different back ends**, with the per-function ISA override
leaking forward into every later function in the translation unit.

### 1b. `ASM_OUTPUT_FUNCTION_PREFIX` — board item #4, and the census cannot see it

`varasm.cc:2192`, an `#ifdef` with no `#else`. **s390 is the only definer and
i386 is not**, so the condition was false for all 47 bases and the body ran
nowhere — a leaked ABSENCE. s390 never emitted

```
.machinemode push / .machine push / .machinemode zarch / .machine "z900"
```

which is the previous board's item #4, "the whole of that target's residual".

Both s390 functions guard on `DECL_FUNCTION_SPECIFIC_TARGET`, so push and pop
are balanced by construction — **converting only 1a would have been a
half-fix, not a partial improvement.**

**AND BOARD ITEM #4 HAS TWO STACKED CAUSES. THIS FIXES THE OUTER ONE ONLY,
AND IS CURRENTLY INERT ON s390 — MEASURED, NOT ASSUMED.** `s390.h:200` gates
the entire `.machine` block — *including the definitions of both macros* — on

```c
#ifdef HAVE_AS_MACHINE_MACHINEMODE   ->  S390_USE_TARGET_ATTRIBUTE
```

and `HAVE_AS_MACHINE_MACHINEMODE` is **defined nowhere in this build**.
`target-specs/configure.ac:3040` probes `as_s390_machine_machinemode` and
deliberately does **not** write it, because `S390_USE_TARGET_ATTRIBUTE` is
`#if`-tested in nine places, one of which selects `SWITCHABLE_TARGET` — and
that one cannot be a run-time answer. `target-caps.h:721` says the same.

So s390 defines **neither** `ASM_OUTPUT_FUNCTION_PREFIX` nor its own
`ASM_DECLARE_FUNCTION_SIZE` here, and `-bracket.sh` ARM 2 reads zero on both
sides (section 3c). The conversion is correct and unobservable for s390 until
that capability is written. PRINCIPLES: *a defect can hide behind another
defect.* **Do not record item #4 as closed.**

### 1c. `ADJUST_INSN_LENGTH` — a dead `#ifdef` in branch shortening, 13 back ends

Four sites in `final.cc` (:404, :1111, :1131, :1368), all `#ifdef`, all false
for all 47 bases because i386 defines nothing. **None of the 13 definers ever
had its insn lengths adjusted**: rx, mips, avr, sh, iq2000, msp430, v850,
rs6000, arc, arm, pa, nds32, aarch64.

Not "merely worse code": the macro corrects a length *after* `insn-attrtab`
computes it, and `shorten_branches` uses those lengths to decide whether a
branch displacement is in range. Too small is a branch the compiler believes
reaches and which does not.

**Stated exactly rather than overclaimed:** aarch64's is the Cortex-A53
erratum 835769 workaround, gated on `-mfix-cortex-a53-835769`, so on a default
aarch64 compilation it is a no-op and **little movement is expected on the
scored board from this back end.** riscv64, s390x and x86_64 do not define it
at all. It is converted because it is a live wrong-code leak on 13 back ends,
not because a number is predicted to move.

### 1e. `ADDR_VEC_ALIGN` — jump-table alignment, and aarch64 was 8x over

Three consumers in `final.cc` (:894, :1153, :2480), and this one hides behind
an **`#ifndef`** rather than an `#ifdef`, which is why it reads as harmless.
`final.cc:485` defines the macro to a private `final_addr_vec_align` whenever
a back end has not — and i386 has not, so **that block was taken for all 47
bases** and the **12 definers never got their own answer**:

```
aarch64 0   vax 0   csky 0   xstormy16 1   sh 2   pa 2   nds32 2
ia64 (CASE_VECTOR_MODE == SImode ? 2 : 3)
nvptx / c6x (JUMP_TABLES_IN_TEXT_SECTION ? 5 : 2)     arm, arc computed
```

**Measured** (`-jumptable.sh`, PRE vs post5, one input path both sides):

```
aarch64   .align 3  ->  .align 0     <- its own answer, at last
x86_64    IDENTICAL  md5 11e4493e06b7   <- defines no macro; the control
```

`aarch64.h:1504` asks for **0**, no alignment, and was given `exact_log2
(GET_MODE_SIZE (mode))` = 3 — **every aarch64 jump table 8-byte aligned when
the back end asked for none.** Same family as the previous board's `.align`
finding, where aarch64 was over-aligning arrays by 4096x; this is the
jump-table half.

**The `#ifdef` at `final.cc:2479` was DEAD.** Its `#else` gave
`exact_log2 (BIGGEST_ALIGNMENT / BITS_PER_UNIT)` and could never be reached,
because the `#ifndef` above had already defined the name for exactly the bases
that would have wanted it. Two fallbacks, one unreachable, disagreeing.

The fallback is supply-side and stays: `final_addr_vec_align` is now
non-static (`output.h`) and the thunk calls **that same function**, so it
cannot drift from the generic answer it is meant to be.

**And the 47-base build's warning count enumerated the population for free.**
`stderr` moved 4762 → 4802, and the whole 40-line delta is **10** `unused
parameter 'table'` from `mt_base_addr_vec_align` — one per base whose macro
ignores its argument. 10 + arm + arc = **the 12 definers exactly**, so the
thunk reached the right back ends and only them. Now `ATTRIBUTE_UNUSED`,
because this branch measures stderr; the enumeration is written into the
comment since it is no longer reproducible from a log.

### 1d. THREE MISSING INCLUDES, AT ONE 47-BASE BUILD EACH UNTIL A HARNESS

Converting a macro whose body is a back end's own code means the per-base
translation unit must now satisfy **that** back end's headers. Each missing
declaration is one `error:` that stops the build:

```
build 1  config/epiphany/epiphany.h:776: `lookup_attribute` not declared
           (ASM_DECLARE_FUNCTION_SIZE, expanded at target-cumargs.cc:313)
build 2  attribs.h:165: `get_identifier_with_length` not declared
           (attribs.h needs stringpool.h ahead of it)
syncheck config/msp430/msp430.h:541: `recog_memoized` not declared
           (ADJUST_INSN_LENGTH, needs recog.h)
```

Each of the first two cost a **full 47-base build**, rc=2, exactly one
`error:`, no `cc1`. This is the loud-signal case PRINCIPLES prefers — the
build names the back end, the file, the line and the identifier — and it is
also the argument for 47 bases: **with the i386+aarch64 pair neither defines
`ASM_DECLARE_FUNCTION_SIZE` at all, so nothing would have expanded and the
omission would have shipped.**

`-syncheck.sh` ends the one-build-per-include cost. It lifts the
`target-cumargs.cc` compile line out of a failed build's own log — so the
flags are exactly make's, including the ~90 `-D<name>=<name>_<base>` renames
no hand-written command would reproduce — rewrites only the three per-base
defines, and runs `-fsyntax-only` for every base against an existing build
dir. It found the msp430 one immediately. **Final state: 47 of 47 bases
syntax-clean.** It is a precondition for a build, not a substitute: it does
not link and does not run the generators.

## 2. THE CENSUS WAS WRONG THREE WAYS, AND THE TOTAL NEVER MOVED

The brief's sizing — `296 = 119 LEAK-PRIMARY + 177 DEAD-DEFAULT` — is the
whole project's remaining scope. All three defects below leave a plausible
total, which is why none had been noticed.

### 2a. The assumed primary chain: 31 macros in the wrong bucket

`-leakcensus.sh` read the chain from a real build's `tm.h` when given `TMH=`,
and otherwise fell back to a hand-written nine-header list, announced with a
`NOTE:` and then used as if measured. `config.gcc:1396` puts
`glibc-stdint.h` in every `*-*-linux*` `tm_file`; the fallback omits it.

```
fallback chain      LEAK-PRIMARY  88   DEAD-DEFAULT 208     total 296
real build tm.h     LEAK-PRIMARY 118   DEAD-DEFAULT 178     total 296
```

The real chain has **16 headers, not 9**, with `config/glibc-stdint.h` at
line 55. The ~31 are `INT8_TYPE` .. `UINTPTR_TYPE` plus `SIG_ATOMIC_TYPE` —
glibc's answers reaching all 47 back ends through `c-family/c-common.cc`'s
`__INT32_TYPE__` and friends. **This reconciles the board's 119/177 with a
fresh run's 88/208: both were correct readings of one tree through two
different chains.** `TMH` is now required; a run without it exits 9.

### 2b. The extraction truncated names: the census could not see `Pmode`

`[A-Z_][A-Z_0-9]*` stops at the first lowercase letter, so `@defmac Pmode`
did not fail to match — **it matched `P`**, which is word-spelled 80 times in
shared code and so always classified into some bucket.

```
@defmac Pmode                   ->  P
@defmac INVOKE__main            ->  INVOKE__
@defmac __builtin_saveregs ...  ->  __
```

So the population carried three garbage names and **was missing `Pmode`** —
the macro PRINCIPLES names first among this branch's leaks, and the one
behind riscv64 emitting 32-bit code into an ELF64 object. Fixed: 543 -> 545,
with arms asserting the truncations gone and the five real names present.
(`Pmode` scores REDIRECT — already converted. The point is that the census
could never have said so.)

### 2c. DESCRIPTOR subtracts live leaks: the population is ~331, not 296

The census subtracts any macro named in a `target-*.h` header. But a
DESCRIPTOR macro is claimed converted **by call-site rewrite**, so a name
still spelled in shared code is still a leak that has been subtracted.

`-descaudit.sh`: **35 of the 94 DESCRIPTOR macros are still spelled raw in
shared code.** So 296 is not the upper bound the board calls it, and the real
figure is about **331**. Board item #3 (`ASM_OUTPUT_MAX_SKIP_ALIGN`) is one of
them — DESCRIPTOR on the strength of one *sentence* in `target-caps.h:314`
while `varasm.cc:2173,2181,2182,2184` and `final.cc:2432,2436,2438` spell it
raw. **The board was right and the census was wrong.**

That audit needed two corrections before its number meant anything, both
recorded in it: a first-character comment test scored multi-line `/* */`
prose as code (73 of 94), and `target-*.cc` was in the "shared" population
though it is compiled once per base (73 -> 35). It carries four NEGATIVE
controls — `ASM_DECLARE_FUNCTION_NAME`, `ASM_OUTPUT_FUNCTION_LABEL`,
`PROMOTE_MODE`, `REG_ALLOC_ORDER` — because a scan that flags everything has
a perfect positive arm and is worthless. All four flagged before the fix,
none after.

### 2d. A FOURTH population the census cannot see AT ALL

`ASM_OUTPUT_FUNCTION_PREFIX` and `ADJUST_INSN_LENGTH` are **not in
`doc/tm.texi`**. The census's population *is* tm.texi's `@defmac` list,
chosen so it "cannot be accused of having chosen its own population" — a real
property, and the reason its figure is quotable. **The authority that makes
it trustworthy is what makes it blind here**, and no number of re-runs
produces these rows.

`-undoc.sh` sizes it: **109 candidates**. Much is noise (`INCLUDE_VECTOR`,
`IN_TARGET_CODE`); the real ones are worth the script:

## 4. WHAT IS NOT IN THIS BOARD — READ BEFORE QUOTING ANY ROW

- **s390x AND aarch64 HAVE NO SUITE RUN HERE, AND I DO NOT CLAIM THEY ARE
  UNMOVED.** Only riscv64 and x86_64 were run (3d). aarch64 is CHANGED by
  construction — `ADDR_VEC_ALIGN` moves its jump-table alignment, measured in
  1e — so "unmoved" is not available as a claim for it and I do not make one;
  what is shown is byte-level. **aarch64 is the one to run first**, for
  exactly that reason.
- **s390x is untested and its two conversions are inert there anyway**, for
  the `HAVE_AS_MACHINE_MACHINEMODE` reason in 1b. A suite run for it would be
  measuring the stacked cause.
- The riscv64 debt figure from `A018835BBCFAD2E28` (772) is **not
  recomputed** here; this board reports transitions against its own PRE, not
  against stock, so it does not update that column.
- **The three causes are separable by TARGET, not by tree.** Only two 47-base
  trees were built (`pre`, `post3`); the intermediate size-only tree failed
  on 1d and was not rebuilt. riscv64 sees 1a alone, s390x the 1a+1b bracket,
  aarch64 1c alone, x86_64 none. That is an argument, not a measurement.
- The `-g` md5 is path-sensitive and is never quoted without its build dir.
- Compile-only; nothing here is an execution result.
- `-undoc.sh`'s 109 is a candidate count, not a leak count. It ranks and does
  not conclude.
- `-descaudit.sh`'s 35 can only REVOKE a DESCRIPTOR claim, never bless one; a
  name absent from shared code is consistent with a real conversion and with
  a macro shared code never spelled.

   undocumented, **12 back ends** including aarch64,
   spelled at `final.cc:894,1153,2479` with an `#ifndef` fallback to
   `final_addr_vec_align` at `:485`. aarch64 asks for `0`, sh/pa/nds32 for
   `2`, vax/csky `0`, arm and arc computed; everyone gets the generic. This
   is jump-table alignment — **the same shape as the `.align` leak the
   previous board found worth 10 assembler out-of-memory failures and a
   4096x aarch64 over-alignment**, one macro over. Highest-value known item.
3. **`ASM_OUTPUT_MAX_SKIP_ALIGN`** — the previous board's item #3, still

   `varasm.cc:2173` and `final.cc:2432`.
4. **The 35 DESCRIPTOR macros in `-descaudit.sh`'s list.** Each is a leak the

5. **The stdint family (2a) is a real LEAK-PRIMARY of ~31 macros and scores

## 6. METHOD NOTES PAID FOR HERE

- **The stale-worktree trap, fourteenth occurrence — and the brief's
  correction is right.** `git merge-base --is-ancestor HEAD multi-target-0`
  returned **1** for my tree, because 30 GCC-12 commits had diverged it; the
  deciding arm is the `rev-parse` equality, which differed immediately. The
  `grep -c MULTI_TARGET` read **0**, the bare-repo value. All three arms
  agreed and cost one turn. Note the environment's own `gitStatus` preamble
  showed the CORRECT tree's branch and recent commits while `cwd` was the
  wrong one — so the harness metadata actively points away from the defect.
  `git reset --hard` was refused by the permission classifier; `git checkout
  -b <new> multi-target-0` is the non-destructive equivalent and loses
  nothing.
- **A control anchored on a conversion target has an expiry date, and mine
  expired within the hour.** `-undoc.sh`'s non-vacuity arm was anchored on
  `ASM_OUTPUT_FUNCTION_PREFIX`, the macro it was written to demonstrate. I
  converted that macro and the arm went quiet. It printed "NOT a pass, treat
  the total as unverified" rather than a green — the wanted behaviour — but
  this is the `macro-probe-run.sh` shape PRINCIPLES records dying unnoticed
  for a day. Re-anchored on `ADDR_VEC_ALIGN` **because it is not being
  converted**.
- **I wrote a false RED into my own guard, of the exact class I had
  diagnosed two commits earlier.** `-drive2.sh` asserted the converted
  snapshot has no raw `#ifdef ADJUST_INSN_LENGTH` with an unanchored
  `grep -q` — which matched that string inside *the conversion's own
  explanatory comment* at `final.cc:404` and refused a correct snapshot.
  "A scan cannot tell a mention from a use" is precisely what I had just
  written about the census's DESCRIPTOR bucket. It cost no build only
  because it fired before `configure`.
- **A SYNTAX SWEEP READ THE SNAPSHOT'S HEADERS AND SCORED 47/47 ON CODE THAT
  COULD NOT COMPILE.** The compile line lifted from a build log carries
  `-I<snapshot>/gcc`, so `-syncheck.sh` compiled the **working tree's `.cc`
  against the snapshot's `.h`** — new code, old headers. A
  `target-cumargs.cc` whose table initialiser names a struct field that
  exists only in the working tree's `target-frame.h` scored **47 of 47 `ok`**
  where it should have been "too many initializers". The tell came from the
  sibling harness: `final.cc` failed with `mt_addr_vec_align was not
  declared`, which reads as a bug in the change and was a bug in the tool.
  Both harnesses now rewrite the snapshot path to `$SRC`. **A harness that
  takes its flags from a real build inherits that build's idea of where the
  source is** — which is exactly what you wanted for the flags and exactly
  what you did not want for the includes.
- **AND THE FIX WAS ONLY VISIBLE BECAUSE TWO HARNESSES DISAGREED.** The
  per-base sweep was green and the shared-TU sweep was red on the same tree,
  at the same commit, for the same change. PRINCIPLES asks that when
  replacing an instrument you run both and require them to agree on what is
  not in dispute; here running two populations is what produced the
  contradiction that found the defect in one of them.
- **A SECOND HARNESS OF MINE REPORTED "THE FIX DOES NOTHING", CONFIDENTLY AND
  WITH A CLEAN CONTROL COLUMN.** `-bracket.sh`'s first run printed
  `push=0 pop=0` on both sides for riscv64, the same for s390x, and
  `IDENTICAL` for both control targets — a complete, plausible report that
  three conversions changed nothing. It had guessed the specs-config path
  (`$d/specs-<triple>-config`; the real one is
  `$d/lib/gcc/<ver>/<triple>/specs-config`), written a 9-byte `NO-SPECS`
  placeholder in an `else` branch, and counted zeros in it. **The control's
  own tell was in the output and I nearly missed it: both targets reported the
  SAME md5**, which two different architectures cannot produce. Only the
  non-vacuity arm named it. `taa-specs.sh:51` records this same path being
  guessed wrong once before. The `else` branch is now gone — a missing
  specs-config exits 9 by name, because a placeholder is a way of continuing
  with no data.
- **AND THE INPUT ITSELF CAN BE THE VACUOUS THING.** The riscv arm then used
  `target("arch=rv64gc_zbb")`, which this build rejects — its riscv defaults
  to rv32 — so both sides produced a 110-byte error file and every count read
  0 again: *the second* "the fix does nothing" from *the same script* for a
  different reason. `norelax` reaches the identical bracket condition and is
  width-independent. Two vacuity bugs in one harness, both failing towards
  "no change", which is the direction that gets believed.
- **MY OWN NEW HARNESS SCORED 22 OF 22 BASES `ok` WHILE COMPILING NOTHING,
  AND ITS NEGATIVE CONTROL IS THE ONLY REASON I KNOW.** `-syncheck.sh`'s
  first run reported every base clean and then failed its own control with
  `g++: command not found` — I had run it outside the nix dev shell, so all
  22 compiles died with `command not found`, emitted no `error:` line, and
  scored as passes. That is PRINCIPLES' "a missing tool looks exactly like a
  zero result", in a harness written the same hour by someone who had just
  read the sentence. The control injects a deliberately undeclared
  identifier and requires the compiler to report it. Without it the sweep
  would have been banked and the next hour-long build would have failed on
  msp430 regardless. **Every scanner in this session needed a negative
  control before its number meant anything** — the DESCRIPTOR audit (four),
  the undoc scan (one), this (one).
- **A wrong split with a right total hides indefinitely.** All three census
  defects (2a, 2b, 2c) preserve a plausible headline: 2a moves 31 macros
  between buckets and leaves 296; 2b swaps a real macro for a garbage one
  that always classifies; 2c removes leaks from a figure already described
  as an upper bound. **Check the decomposition, not the total** — the same
  lesson the probe scoreboard learned when it started printing its own.
- **The census's trustworthiness and its blind spot are the same property.**
  Deriving the population from `tm.texi` is what makes the figure defensible
  and what makes ~109 undocumented candidates invisible. That is not a bug to
  fix in the census; it is a second instrument to own beside it.
