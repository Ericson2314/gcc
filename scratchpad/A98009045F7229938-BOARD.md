## 2. IT WAS TEN, NOT ELEVEN, AND THE ELEVENTH IS A REAL CORRECTION

The brief and `A7D26223EEFCFA725-BOARD.md` §4 both name eleven:

```
avr  cris  ft32  h8300  mmix  moxie  msp430  pdp11  rl78  vax  xstormy16
```

Measured at `f12a610e587`, **ten** emit that diagnostic. `mmix` has no
automaton — it is in the 14 below — but it never reaches the gate:

```
mmix  ICE  back end 'mmix' has no assembler-directive table; gen-multi-target-md.awk
           omits one for mmix and for the back ends sharing default-common.cc
```

It is refused earlier, by a different defect, **before** and **after**. So
fixing the DFA gate does not make mmix compile and never could have. The board
was taken at `4387bf9ce42` and this at `f12a610e587`, so the honest statement
is *"ten at this commit"* rather than *"the board was wrong"* — but anyone
carrying the list of eleven as a to-fix list will be one short of a green and
should look at the asm-directive table, not at scheduling.

Nine of the ten now emit; the tenth, **msp430**, advances from the DFA ICE to
its own previously-recorded wall (`msp430_function_section`,
`config/msp430/msp430.cc:2466`), which the board already lists under
DIED-FIRST-INPUT. That is a fix, not a residual of this one.

## 4. THE FIX, AND THE THREE THINGS DELIBERATELY NOT FIXED

`mt_has_insn_scheduling ()` reads `targetm_automata->has_dfa`, i.e. that
base's own `#ifdef INSN_SCHEDULING` evaluated in `target-cumargs.cc` compiled
for that base. A **query**: it answers `false` for a base with no automaton,
and still refuses when no base is selected, because a `false` there would be
an invented answer and, being the quiet direction, would silently disable
scheduling for everyone.

Converted (7 gates): `pass_live_range_shrinkage`, `pass_sched`, `pass_sched2`,
`pass_sched_fusion` (`sched-rgn.cc`), `pass_sms` (`modulo-sched.cc`),
`enable_split_before_sched2` and `gate_split_before_regstack` (`recog.cc`).
The query goes FIRST in each `&&` so a base that cannot schedule does not
consume a `dbg_cnt` tick either.

**The ICE was in `sched1`, not `sched2`** — `-fschedule-insns` is
`OPT_LEVELS_2_PLUS_SPEED_ONLY`, so it is on at `-O2` and runs first.

NOT converted, each a decision rather than an oversight:

- **The file-scope `#ifdef INSN_SCHEDULING`** in `haifa-sched.cc`,
  `sched-deps.cc`, `sched-ebb.cc`, `sched-rgn.cc`, `modulo-sched.cc`,
  `ddg.cc`, `sel-sched*.cc`, `sched-int.h`. They decide whether the scheduler
  is COMPILED IN, and in a build containing any back end with an automaton it
  must be, for that back end. That is the union's presence used as the union's
  presence, which is correct. What was wrong was using it as the selected
  base's answer.
- **`opts.cc`'s two `default_options_table` entries.** `opts.o` is in
  `libcommon-target.a`, which the DRIVER links; `targetm_automata` is in
  `libbackend.a`, which it does not. A call there does not link — the same
  boundary `gcc/Makefile.in` already records for `$(MT_OPTIONS_TABLES_OBJS)`.
- **`toplev.cc:1428`'s warning, FOR THE SAME REASON**, and this is the
  half-fix trap in the concrete. Converting it while `opts.cc` still sets
  `-fschedule-insns2` at `-O2` would emit *"instruction scheduling not
  supported on this target machine"* on EVERY `-O2` compile for the ten — a
  new diagnostic on every test, from a change whose purpose was to remove one.
  The two are a matched pair and must move together, into `targetm_common`
  (which IS selected before `decode_options`, `toplev.cc:2407`). Until then
  the observable is unchanged, because the pass gate and not the flag is the
  authority.

## 5. BOTH-SIDED — 29 identical, 9 fixed, 0 regressions

`a98009045f7229938-bothsided.sh`, every target with a `specs-config` in both
builds, `-O2`, emitted assembly compared byte for byte:

```
HAS an automaton : IDENTICAL 29   DIFFERS 0
NO  automaton    : IDENTICAL  0   DIFFERS 0   FIXED 9
```

The change adds one conjunct to seven gates; for a back end with
`has_dfa == true` that conjunct is the constant `true`, so any byte of
difference in that population is a finding. **The partition is predicted
before it is measured**, and the script refuses two null results: zero DFA
back ends compared (what a broken map prints, and also what "no regressions"
prints), and zero DFA-less targets changed (which would make the IDENTICAL
column evidence about the fixture rather than the fix).

**Its first draft got three rows wrong**: it mapped triple → back end by
prefix, so `x86_64-pc-linux-gnu` (i386), `hppa64-…` (pa) and `powerpc64-…`
(rs6000) were all labelled `NO-DFA`. It did not change the verdict — all three
were IDENTICAL either way — and it would have inverted it for any that moved:
a regression in a back end that must not differ would have been filed in the
bucket that is allowed to.

## 6. THE INSTRUMENT DEFECT, SWEPT RATHER THAN MET ONCE

`causes2.sh` already folded `back end '<x>'`, which is why the DFA case became
visible at all. That fold was written for the message that had been noticed
and nothing asserted it covered the population.

`a98009045f7229938-foldcheck.sh` is that assertion: **29 `%qs` refusals** in
the selector sources, and one the fold cannot reach —

```
target 'avr-unknown-elf' names back end 'avr', which was not built into ...
```

— whose first field is a target TRIPLE, so folding the back-end name collapses
nothing and 47 targets key as 47 causes. The same masking in a message that is
not `back end %qs`-shaped at all. `causes2.sh` now folds `target '<t>'` too.

**The checker's own first draft reported a clean 28/29**, because it asked
"does this contain `back end %qs`" and three messages contain it *and* a
second varying `%qs`. ARM 2b exists because of that miss, and the rule it
draws is the durable part:

> fold every field that varies with the **target**;
> fold no field that varies with the **defect**.

Two of the three residuals hold a MACRO name and one holds a SYMBOL name.
Those must stay split — two back ends failing on different macros are two
causes, and folding them would hide a second defect behind a first, the mirror
of the bug being fixed.

## 8. A SIBLING LEAK THE CENSUS FOUND FOR FREE — `DELAY_SLOTS`

The other macro `genattr-common` writes into `insn-attr-common-<base>.h`, and
the primary's in shared code for exactly the same reason:

```
insn-attr-common.h    DELAY_SLOTS 0   (== i386's)
12 of 47 say 1 -- arc cris fr30 h8300 iq2000 microblaze mips or1k pa sh
                  sparc visium -- all answered by i386's 0.
```

Visible in the same census run, on arc:
`cc1: warning: this target machine does not have delayed branches`. The
consequential half is `reorg.cc:3838`/`:3878`: **delay-slot filling has never
run for any of the twelve on this branch**, and `function.cc:6766` asserts
`gcc_assert (!DELAY_SLOTS)` — an assertion that holds only because the answer
is wrong.

**The shape is the transferable part and it is NOT the `#ifdef` shape.**
`DELAY_SLOTS` is already a 0/1 value and its consumers already spell
`if (DELAY_SLOTS)`. So "the consumers are runtime `if`s" is not evidence a
macro is per-base here. An audit grepping for `#ifdef` scores this clean.

Deliberately left: turning it on starts running `reorg` on twelve back ends
for the first time, which is a different size of change from switching a gate
OFF, and deserves its own both-sided measurement.

## 9. A THIRD LEAK, ONE BACK END WIDE — `GO_IF_LEGITIMATE_ADDRESS`

fr30's `-O2` ICE is `default_legitimate_address_p, at targhooks.cc:115`, which
is a bare `gcc_unreachable ()` under `#else`. `targhooks.cc` is shared, so the
`#ifdef GO_IF_LEGITIMATE_ADDRESS` is the primary's — and **fr30 is the only
back end in the tree that defines that macro**. Invisible to any pair, and to
almost any base set. Same class, one back end wide.

I ran `pkill -f mtcheck` to stop my own suite run. **Two other agents had
`mtcheck.sh` runs in flight on this box** (`b-a260445cf27ba480a-cxx`,
`b-a95a42fd940ce4d8e-post`). They survived; nothing in what I typed made that
happen. A killed `mtcheck` leaves a stale `check-<triple>.rc` beside a PARTIAL
`gcc.sum` — INSTRUMENTS.md's own recorded shape — so the damage would have
been a wrong green in someone else's board, hours later, with no way to
attribute it.

`/tmp` and the process table are shared exactly as the git index is. Kill by
PID, or by a pattern carrying the full worktree id; never by the name of a
harness every agent runs.
