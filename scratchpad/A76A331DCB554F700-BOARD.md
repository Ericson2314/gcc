## 0. THE TIP DID NOT BUILD, AND THE FAILURE WAS ONE MERGE

```
$ make all-gcc          # immutable git archive of 3f75b7f16a3, in the dev shell
c-family/c-cppbuiltin.cc:1638: error: `mt_has_eh_return_stackadj_rtx'
                                      was not declared in this scope
make: *** [Makefile:4837: all-gcc] Error 2
```

`803794e7c6b` names its own three conflicted files. It resolved them by taking
`ea67506378f`'s copy whole. I re-ran the three-way merge from the real base
(`e1f0cad1c2c`): **in all six conflict hunks `theirs` is a strict superset of
`ours`**, so the choice inside the conflicts was right. What a whole-file take
throws away is everything the other side added *outside* a conflict — here the
entire `EH_RETURN_HANDLER_RTX` / `EH_RETURN_STACKADJ_RTX` / `TRAMPOLINE_SECTION`
conversion: 328 lines of `target-frame.h`, 140 of `target-cumargs.cc`, 115 of
`target-cumargs-select.cc`.

**Why it was loud rather than silent, and why nobody heard it.** The consumers
were never conflicted and all survived. That is exactly what `5d1dd487000`
designed for when it `#undef`'d the macro instead of redirecting it:

> a redirect would … make any site I failed to convert *silent*. With the
> `#undef`, a missed site is a compile error naming the macro. **The build is
> the check.**

The build was the check. It caught a merge rather than a missed site, and the
tree sat red because nothing ran it. **`git merge` reporting "Conflicts:" is
not the same event as a conflict being resolved correctly, and only a build
can tell them apart.**

## 2. THE ONES THAT DIED ON THEIR FIRST INPUT

Each contributed **no FAIL rows at all**, which in a `.sum`-based ranking is
the same object as "never attempted" and as "passed everything".

**`msp430` — the leaked-absence class, and the assert was not msp430's bug.**
`USE_SELECT_SECTION_FOR_FUNCTIONS` is defined by exactly one back end and not
by the primary, so the `#ifdef` in shared `varasm.cc:675` was false for all 47
and the guarded arm ran for nobody. The `#else` arm calls
`targetm.asm_out.function_section` unconditionally, and msp430's hook opens
`gcc_assert (DECL_SECTION_NAME (decl) != NULL)` — an assumption it may make
upstream *because* the macro diverts the no-section case elsewhere. Now a
`bool` in `target_asm_ops`, the table already compiled once per back end
against that base's `tm-<base>.h`. **Default `false` is what every non-definer
has always got, so no other base can move** — and none did (§5).

**`m68k` — a third option-default spelling.** `m68k.h:30` is `-%(VALUE)`: the
value *is* the option. The generic arm wrote `-mcpu=m68020`, which the m68k
driver rejects outright, so the driver died before emitting a `cc1` line and
the failure surfaced three layers away as broken specs plumbing. Transcribed
into `target-specs/configure.ac` beside the existing `i386:`, `mips:` and
`riscv:` arms.

**The design question this does NOT answer, stated rather than dropped:** that
table restates `tm.h` by hand and nothing can diff the two. One authority
guessing another's spelling is this branch's root bug; the transcription makes
m68k right without making the arrangement right.

## 3. THE ARRAY IS THE UNION'S, THE WALK IS THIS BASE'S — now on the MODE axis

`reginfo.cc` and `function-abi.cc` already carry that rule for REGISTERS, in
comments citing an ASAN trace. The MODE axis had never been applied, and
`genmodes.cc` had already written down both the shape and the gap:

> the property that makes a hole safe everywhere else is that `FOR_EACH_MODE*`
> never walks into one, so the question is never asked; **the residue is code
> that reaches a mode by ORDINAL rather than by walking.**

Four such walks hand a shared-numbering ordinal straight to a back-end hook:

```
reginfo.cc:619       init_reg_sets_1
reginfo.cc:708       init_reg_modes_target
reginfo.cc:879       choose_hard_reg_mode   (the CCmode tail loop)
function-abi.cc:79   predefined_function_abi::initialize   x3
```

`pru_hard_regno_mode_ok` closes with `default: gcc_assert (mode == BLKmode ||
mode == VOIDmode)` — true of every mode pru HAS. The union carries sizes pru
never defined. `MODE_IS_HOLE_P` (machmode.h) reads the `0xffff` marker already
emitted per base in `mode_class_index[]`; it is stricter than
`GET_MODE_CLASS (m) == MODE_RANDOM`, which is also true of `VOIDmode` and
`BLKmode`.

**The three reginfo sites alone did not fix pru — and that is how the fourth
was found.** The backtrace moved from `init_reg_sets_1` to
`predefined_function_abi::initialize`, naming the remaining site exactly. A
partial fix that moves a backtrace is worth more than a guess at a complete
one.

**One mode walk in `function-abi.cc` deliberately keeps NO guard.**
`caller_save_regs` walks modes but only reads `mode_clobbers`, a table this
code owns. Guarding it would suggest the criterion is "walks modes" when it is
"asks the back end".

**`mmix` could not be SELECTED, and the exclusion said when it should end.**
`gen-multi-target-md.awk` omitted `target-asm-ops-mmix.o` because
`mmix_data_section_asm_op` lives in `mmix.cc`, "not linked unless mmix is the
primary" — and stated its own end condition: *"this exclusion ends when the
per-back-end compiler objects go into OBJS"*. They have:

```
nm mt-mmix/mmix.o | grep data_section_asm_op   -> T _Z24mmix_data_section_asm_opv
nm gcc/cc1        | grep mmix_data_section     -> T _Z24mmix_data_section_asm_opv
```

While it stood, mmix was the only back end of 47 with no entry in
`targetm_asm_ops_registry`, so `multi_target_select` refused it by name on
every input — a perfect diagnostic that nothing was reading. **A condition
that has been met is not self-cancelling.** Removing the exclusion then failed
the build by name (`mmix_data_section_asm_op' was not declared`), because
`target-asm-ops.cc` included only `tm-<base>.h` and a back end declares such
functions in its `<cpu>-protos.h`; fixed with `TM_P_H_FILE`, the same series as
`target-cumargs.cc`'s epiphany/`attribs.h` and msp430/`recog.h`.

## 4. TOOLS — a recorded figure that measures FALSE

`A7D26223EEFCFA725-BOARD.md` quotes *"45 cross `as`, canonical names, **every
one EXECUTED**"*. Re-run today, **8 of those 45 do not execute**:

```
m68k microblaze mmix msp430 powerpc64 rx sh sparc64
  error while loading shared libraries: libopcodes-2.46.so
```

They were gathered **by copy** out of nix store paths; the binaries link
dynamically against libopcodes/libbfd in their own store output, and a copy
leaves that behind. **"Every one executed" was true when taken and is not a
property a copy keeps** — the same shape as the `.sum` that a stamp says
finished but that no longer belongs to that run. Note both of the eight that
matter most here: msp430 and m68k are two of the four this task was sent to
fix.

Rebuilt via `crossSystem`, and six of the eight needed a different nixpkgs
SPELLING (`m68k-elf` for `m68k-unknown-elf`, and so on). An `EVAL-FAIL` is a
statement about `lib.systems.parse`, not about binutils — that distinction is
already in INSTRUMENTS.md and it is what made the recovery possible.
`sh4-elf` for `sh-unknown-elf` is flagged as SUBSTITUTED, not a pure
respelling. `powerpc64` has no working `as` here under either spelling and is
reported **AS-ABSENT — never scored against the host `as`.**

## 6. WHAT IS *NOT* HERE — UNKNOWN, never zero

- **No `.sum` run.** This board is compile-and-assemble only. It says the
  nineteen can now be *put through* the suite; it does not say what they score.
- **No stock control on any row.** No debt figure for anything here.
- **No authored `scan-assembler` tests were committed.** The brief authorises
  them, and the foundation for them now exists (§1). Validating one needs a
  **stock single-target cross per back end**, which I did not build — and a
  test that only passes on this branch is testing our bug. Committing nine
  unvalidated test files would have been exactly the unfalsifiable claim
  PRINCIPLES §"PASSING TESTS COME BEFORE SIMPLIFYING" warns about. **This is
  the largest thing left undone and it is the next task, not a footnote.**
- **`pa` was not addressed**, and `sparc`'s `LEAF_REGISTERS` stub is
  unchanged — it is a fail-by-name stub working as designed, not a defect.
- **`nvptx`'s remaining ICE is located, not fixed**:
  `gcc_checking_assert (init_frag.active)` at `nvptx.cc:2388`, reached from
  `assemble_variable_contents` on a file of plain globals. Whatever starts a
  data fragment is not running — the same family as the leaks in §2, and it
  needs its own measurement.
- **`-march=sm_30` is REJECTED BY THE DRIVER for nvptx** while nvptx's own
  `-march-map=` is accepted and `-misa=` works. That is the m68k defect in the
  option table rather than the spec file, and it is recorded, not worked
  around.
- **Stability was not tested.** PRINCIPLES records mips64 giving 5 rc=0 and 7
  SIGSEGV in twelve identical runs. Every row here was taken once.
- **The corpus is 7 small files.** "Compiles and assembles correct-machine ELF
  for 7 inputs" is exactly the claim, and no larger one.
