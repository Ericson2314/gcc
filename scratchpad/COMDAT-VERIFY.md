# COMDAT sweep re-run against the FIXED tree -- verification only

Nothing committed, nothing staged, no tracked file edited.  Private worktree
`/tmp/mt-verify-src` (detached at `642e63adc6c`, `git status` clean) and private
build dir `/tmp/b-verify`.  `/tmp/b-objs` was not written.  The user's tree was
read only; it currently carries seven other agents' uncommitted edits, which is
exactly why the verification build came from a detached worktree at the commit
rather than from the working tree.

Verdict up front: **the class is CLOSED for all four named hazards, and the two
previously-judged non-hazards are CONFIRMED.**  0 real hazards out of 1064
compared names.  But the instrument that says so has blind spots, and looking
into one of them turned up a *different* live divergence that no COMDAT sweep
can ever see -- see "What the instrument cannot see", item 1.

## Per-name verdict -- all six names

Instrument: `scratchpad/cv-sweep.py` (per-name report) and
`scratchpad/cv-classify.py` (classification).  Full output in
`/tmp/cv-sweep.out`, `/tmp/cv-cls2.out`.

  1. **`optab_handler(optab_tag, machine_mode)` -- FIXED.**
     13 defining objects across all three sets.  Every one of them reaches
     `selected_raw_optab_handler`; not one reaches `raw_optab_handler`,
     `insn_i386::raw_optab_handler` or `insn_aarch64::raw_optab_handler`.
     The only variation left is the ORDER of the two relocations
     (`fancy_abort` before or after `selected_raw_optab_handler`), which is
     scheduling, not meaning.

  2. **`convert_optab_handler(...)` -- FIXED.**  10 defining objects, all
     reaching `selected_raw_optab_handler`.  Same order-only variation, plus
     `convert_optab_p` inlined in some copies and not others.

  3. **`get_cumulative_args(cumulative_args_t)` -- FIXED.**  Defined in
     `mt-i386/i386.o` and `mt-aarch64/aarch64.o`; both bodies now hold exactly
     one relocation, to `fancy_abort`.  No `targetm`, no `targetm_i386`, no
     `targetm_aarch64` in either.  The magic is an immediate now, and the
     immediate is the same one in both (22 occurrences of `0x4d41474943` in
     `cc1`, zero occurrences of an `&targetm*.calls` address).

  4. **`estimated_poly_value(poly_int<2u, long>, ...)` -- FIXED.**  Defined in
     `i386.o` and `aarch64.o`; both bodies are a single call to
     `estimated_poly_value_1`.  The `<1u>` overload is not emitted anywhere,
     as expected -- `NUM_POLY_INT_COEFFS` is 2 for both bases since
     `8cd2e85cdf8`.

  5. **`direct_optab_handler(optab_tag, machine_mode)` -- previous judgement
     CONFIRMED, and now for a second reason.**  It is emitted weak in exactly
     two objects (`aarch64-acle-builtins.o`, `aarch64-sve-builtins-base.o`),
     both bodies a bare tail call to `optab_handler`, identical.  It never had
     a per-back-end name of its own and it inherits a fixed callee now.

  6. **`test_register_filters()` -- previous judgement CONFIRMED as stated, and
     the caveat is worth MORE than the verdict.**  It is emitted weak in NO
     object in this build (fully inlined everywhere), so it is not a COMDAT
     collision in a two-target configuration.  But it is still bare and it is
     still two different functions:

         tm-preds-i386.h     test_register_filters (unsigned, unsigned) { return true; }
         tm-preds-aarch64.h  test_register_filters (unsigned mask, unsigned regno)
                             { for (id = 0; id < 4; ++id) ... }
         tm-preds.h          == the i386 one   (the middle end's copy)

     and `insn-config.h` -- shared, unioned -- says `NUM_REGISTER_FILTERS 4`.
     So the middle end (`ira-color.cc` has four call sites) is compiled to
     size register-filter masks for four filters and to answer "yes, any
     register is allowed" for all of them.  That is a wrong answer for aarch64
     already, with one configured aarch64 back end, and it is invisible to
     every object-level sweep because there is only ever one inlined copy.
     **Not a COMDAT hazard; a live per-base-body-in-a-shared-header hazard.**

## Is the class closed, or moved?

Closed, for these four, by the criterion that matters: after normalising away
relocation ORDER, 314 of 1064 compared names have differing relocation SETS,
and **0 of those differences name anything per-back-end** (`insn_i386::`,
`insn_aarch64::`, `targetm_i386`, `targetm_aarch64`).  The 314 are ordinary
inlining variation between translation units -- `tree_check` inlined here and
called there, `bmp_iter_next_bit` folded in one copy -- which C++ permits and
which has no target in it.  Nothing moved to a new name: `selected_raw_optab_handler`
and `estimated_poly_value_1` are `T`, singular, out of line, in one object each.

**Positive control, because a 0 from an unexercised instrument is worth
nothing.**  I compiled a scratch object pair into the build dir -- one inline
`comdat_control_probe` with the same mangled name whose body calls
`insn_i386::probe_raw` in the middle-end copy and `insn_aarch64::probe_raw` in
the aarch64 copy, i.e. the exact pre-fix shape of `optab_handler` -- and re-ran
the classifier unchanged:

    === bodies differing as SETS: 315 ===
    === of those, whose difference names a per-back-end symbol: 1 ===
    HAZARD comdat_control_probe(unsigned int)
       differs in: ['insn_aarch64::probe_raw(unsigned int)', 'insn_i386::probe_raw(unsigned int)']

One planted hazard, found; the real count stays 0 around it.  The two scratch

## What the instrument cannot see

Stated as findings, not as caveats, because the standing lesson on this project
is that a clean result from an unexamined instrument is worth very little.

  1. **A per-base MACRO, which has no symbol and no relocation.**  This is not
     hypothetical.  I extracted every `#define` from the per-base generated
     headers (12848 for i386, 16443 for aarch64), took the 836 whose *name* is
     shared and whose *value* differs, and grepped the shared headers for them.
     Six hits, and four are a live divergence nobody has recorded:

         CONST_MODE_NUNITS      i386 `const'   aarch64 (empty)   machmode.h:28
         CONST_MODE_PRECISION   i386 `const'   aarch64 (empty)   machmode.h:26
         CONST_MODE_UNIT_SIZE   i386 (empty)   aarch64 `const'   machmode.h:29
         CONST_MODE_MASK        i386 `const'   aarch64 (empty)   machmode.h:747

     `machmode.h` declares `extern CONST_MODE_PRECISION poly_uint16
     mode_precision[NUM_MACHINE_MODES];` and the shared `insn-modes.h` is the
     i386 one, so the middle end declares four arrays `const` that every
     aarch64 object declares non-`const`.  Same object, two types, no
     diagnostic.  (`nm -S insn-modes.o` puts `mode_nunits` and `mode_precision`
     in `.bss` today, so this is currently an ODR/type divergence rather than a
     write to read-only memory -- but the reason aarch64 wants them mutable is
     that it adjusts mode sizes at startup for SVE, so the shape is one write
     away from a segfault, and the mode-numbering union commit did not touch
     `CONST_MODE_*`.)  **Not in scope here, and not fixed; reported because the
     COMDAT sweep structurally cannot reach it.**
     The other two hits, `HAVE_cpymemdi`/`HAVE_setmemdi` in `defaults.h`, are a
     false positive of that instrument: the values differ (`(TARGET_64BIT)`
     against `1`), but `defaults.h` only tests `defined(...)`, and both bases
     define them.

  2. **A body that is inlined to nothing in one base.**  `test_register_filters`
     is the standing example, and this run reproduces it exactly: absent from
     all three object sets, so the sweep skips it silently.  A name that only
     one configured back end even instantiates cannot be compared, and a hazard
     that needs a THIRD configured target to exist cannot be seen at two
     targets by any instrument built from object sets.

  3. **Weak symbols with no code.**  11 candidates in this run had fewer than
     two disassemblable copies -- weak *data*: vtables, `typeinfo`, inline
     variables, static data members.  `objdump -d` shows nothing for them, and
     both this sweep and sweep4 skip them without saying so (sweep4's `continue`
     was silent; cv-sweep.py at least counts them).  A per-back-end weak *table*
     would be invisible.

  4. **Relocation targets that differ only in ADDEND.**  Both sweeps cut the
     target at `+`/`-`, so two copies reaching different members of the same
     structure -- exactly the `&targetm.calls` shape that started all this, had
     it survived as a relocation -- read as identical.

  5. **sweep4 compared only the FIRST object in each set** (`mid[n][0]`,
     `be[base][n][0]`).  A name differing between two middle-end objects, or
     between two objects of the same back end, was invisible to it.  cv-sweep.py
     compares every copy in every object; that is most of why 314 differ here
     against 8 there, and it is also why the order-insensitive re-normalisation
     in cv-classify.py was necessary to get a usable signal back.

  6. **sweep4's candidate set was `middle-end INTERSECT back-end`.**  A name
     weak in BOTH back ends but not in the middle end was not a candidate at
     all.  There are 395 such names in this build; they are included here and
     none is a hazard, but the earlier 8/4 was over a set that excluded them.

  7. **Build-flag dependence.**  `-O1` here against `-O2` in `/tmp/b-objs`
     changes the middle-end weak-definition population by 7x.  Any absolute
     count from either is a property of the build, not of the source.
