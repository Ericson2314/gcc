## 0. `multi-target-0` could not configure gcc at all

`gcc/gen-target-manifest.sh` carried a hard shell syntax error from
`b1d30fa6d35`. Every worktree cut from the branch tip inherited it, and **no
build of the tip can have succeeded** since that commit:

```
gen-target-manifest.sh: line 372: syntax error near unexpected token `('
make: *** [Makefile:4804: configure-gcc] Error 1
```

The mechanism is worth carrying because reading the file does not find it.
Line 372 is a comment containing a GNU-style `` `word' `` quotation — one
backtick. At the top level that is harmless. But line 117 opens a **multi-line
command substitution** spanning to line 328, and the shell's scan for the
closing backtick does **not** honour `#` comments, so two GNU-quoted words in
comments at lines 219 and 221 silently re-paired the substitution boundaries.
The imbalance surfaced 150 lines later, **naming a line that is correct in
itself**.

It is also invisible to the harness's own summary. The failing artefact is a
*configure* script, so `mt-build.sh` reports `error: 0`,
`multiple definition 0`, `undefined reference 0`, `Killed 0` — every count
clean — and only `rc=2` says anything happened.

`scratchpad/mt-shcheck.sh` is now the standing check: `sh -n` over all 1107
committed `.sh` (with a negative control that must fail), plus a second,
never-fatal arm counting **odd-backtick comment lines** — **3118** of them.
None is an error today; each becomes one the moment a multi-line backtick
substitution grows past it. Prefer `$(...)`: its scan honours comments, so this
class cannot occur inside one.

Residual: **1 of 1107** files still fails `sh -n`, `scratchpad/t132-neigh.sh`,
unrelated to this task.

### 2a. Refused by the top-level configure, by name

Each was established by running `configure` and reading its refusal, one
language at a time:

```

rust    configure: error: cargo is required to build rust
jit     configure: error: Enabling language "jit" requires --enable-host-shared
```

The first three are **host prerequisites, not defects on this branch**. `jit`
is different: the flag exists (`configure.ac:2331`) and upstream's own advice

compiler PIC and would move the x86_64 codegen bar. It is deferred, not

**This matters for the brief's headline.** `d/` and `ada/` are the *only*
readers of `WCHAR_TYPE_SIZE`, and they are two of the three languages this
host cannot build. The defect is real and measured (see §3) and remains
**latent and unexercisable here** — a "cannot tell" that is debt, not a clear.

### 2b. Two build defects, both new, both reachable only now

**`libgcobol/cobol-endian.h:50` — `BYTES_BIG_ENDIAN` was not declared.** On
this branch the name is `(targetm_cdata.bytes_big_endian)`
(`multi-target-macros.h:380`), reached only through `target.h` → `tm.h` →
`defaults.h:1932`. Three `cobol/*.cc` each decided **by include order** whether
the name existed; g++ said so itself (*"had not yet been defined … it was later
defined here"*) and offered `SSO_BIG_ENDIAN`, a real and unrelated identifier,
so the obvious repair is a plausible wrong answer. Fixed by naming the
dependency in the header that uses it. **cobol now builds and `cobol1` runs.**

**`$(generated_files)` expands to nothing in all fourteen `Make-lang.in`.** GNU
make expands a prerequisite list when the rule is *read*; `@language_hooks@` is
`gcc/Makefile.in:3113` and the assignment is `:5339`. Upstream survives it —
`$(ALL_HOST_OBJS) : | $(generated_files)` covers host objects and nothing else
needed it. Here `tm.h` → `defaults.h` → `multi-target-macros.h:243` reaches the
**generated** `multi-target-reg-widths.h`, so any compilation opening `tm.h`
needs it, and two m2 targets are in no barrier at all: `m2/gm2spec.o` is a
*driver* object (`GM2_OBJS`), and `plugin/m2rte.so` is not an object. Both
raced and lost under `-j8`. Fixed by naming the two files literally.
**Partial by construction**, and it says so: thirteen fragments still carry the
dead `$(generated_files)`.

### 2c. m2 does not build, and the remaining cause is a design question

```
m2/gm2-gcc/m2configure.cc:56: error: 'DEFAULT_TARGET_MACHINE' was not declared
```

`DEFAULT_TARGET_MACHINE` is supplied by `-D…=$(target_noncanonical)` from each
front end's `Make-lang.in`, and **`target_noncanonical` is deliberately empty
on this branch** — `gcc/configure.ac:3369` and `gcc/Makefile.in:938` both say
so in as many words. m2's fragment never had the `-D` at all, so it fails
loudly.

**`go` has the identical defect and it is silent.** `go/Make-lang.in:245`
passes `-DDEFAULT_TARGET_MACHINE=""`, and `go/go-lang.cc:240,251` uses it to
build the Go package search path:

```c
strcat (p, DEFAULT_TARGET_VERSION);
if (stat (p, &st) == 0 && S_ISDIR (st.st_mode))
  { go_add_search_path (p);
    strcat (p, DEFAULT_TARGET_MACHINE);      /* "" */
    if (stat (p, &st) == 0 …) go_add_search_path (p); }
```

so the per-target Go package directory is never searched and the same
directory is added twice. Guarded by `stat`, hence silent. `rust/Make-lang.in`
carries the same line.

**One defect, two front ends, one loud and one silent** — and the loud one is
the one that cannot be shipped. Not fixed here: what libexec directory a
compiler with no primary looks in is a *design* decision (PRINCIPLES §2b), and
the honest answers are a run-time read of the selected target or a
fail-by-name, not a baked string. Reported rather than invented.
