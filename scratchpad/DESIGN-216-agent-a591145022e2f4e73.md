## 0. THE HEADLINE: THE SIX ARE **NOT** ONE MECHANISM. THEY ARE THREE, AND THE TREE ALREADY HAS ALL THREE

The brief's grouping — *"one legacy `${target}`'s answer imposed on 47 bases,
landing on a `#if` line"* — is right about the **cause** for five of the six and
wrong about the **remedy** for all of them, because the remedy is decided by
what the `#if` *produces*, not by what feeds it. PRINCIPLES already says this
("position of use decides shape"); the six split cleanly on it.

And the more useful finding is that **no new mechanism needs designing.** Three
channels exist, each landed and each with a worked example in the tree:

| # | channel | where it already works | what it carries |
|---|---|---|---|
| **C1** | **per-TRIPLE compile of the tm.h chain** — `gen-target-specs-<key>` | `gcc/gen-multi-target-md.awk:1194-1211` | the `#if` is evaluated **N times, once per configured triple**, and the *result* leaves as spec text |
| **C2** | **named-spec pair + run-time choice** | `gcc/config/sol2.h:282-330` + `target-specs/configure.ac:3501-3507` | a probe-dependent choice between two spec strings |
| **C3** | **`targ_caps` field read as C** | `gcc/config/sol2.cc:324,330,336,345` | a probe-dependent choice inside back-end code |

C1 is the one the brief was reaching for and did not name. Its own comment
states the property that closes most of this task
(`gen-multi-target-md.awk:1162-1165`):

> *"This triple's source-derived spec file ... **Per TRIPLE and not per back
> end**, which is the whole reason it is emitted here: `LINK_SPEC`,
> `STARTFILE_SPEC` and the rest are exactly the macros that differ between
> `x86_64-linux-gnu` and `x86_64-elf` while both are the i386 back end."*

`gcc/gen-target-specs.cc:30-37` says the same from the other side, and states
the boundary that decides C1-vs-C2:

> *"It is compiled once per configured target against that target's
> `tm-<base>.h` ... **THE BOUNDARY.** Source-derived here; probed in
> `target-specs/`. If a value depends on which assembler or linker is
> installed, it does not belong in this file."*

Measured, the per-triple compile really is per triple:

```
gcc/gen-multi-target-md.awk:1198
  -DTM_HEADER='"tm-<key>.h"' -DTARGET_TRIPLE='"<triple>"'
gcc/gen-multi-target-md.awk:1093-1100
  tm-<key>.h: ...   INSN_BASE="<cpu>" $(SHELL) mkconfig.sh tm-<key>.h
    # "INSN_BASE is the BACK END, not the triple"
```

so `key` = triple and `cpu` = back end are two different axes and the build
already carries both. **`gencondmd` is on the triple axis too**
(`:1112-1123`: `build/genconditions-<key>.o` with `-DTM_H_FILE='"tm-<key>.h"'`
and `-DGENCONDMD_TM_H='"tm-<key>.h"'`), which matters for #21 below.

### THE DECISION PROCEDURE

For any `#if <X>` in a target header, ask **what the arms differ in**:

1. **spec text** → C1 if `<X>` is source-derived; C2 if `<X>` is probed.
2. **a value back-end C code reads** → C3 (`targ_caps`), or the existing
   per-base `target_frame_desc` / `target-cdata` if it is source-derived.
3. **a file installed on disk** → neither. It needs a per-target *artefact*
   directory, and that is a fourth thing (#192, §4).

Applying it: **#69, #25 and half of #100 are C1/C2 and are small. #21 is C3 and
is medium. #26 is already converted and only needs two dead arms adjudicated.
#192 is not this mechanism at all.**

### AND THE BIGGER #26 FINDING THE DEFECT WAS SITTING ON

`gcc/cppdefault.cc:172-182` is the real item, and it is a **C1 case that is
currently answered by the primary**:

```c
  static struct default_include table[]
#ifdef INCLUDE_DEFAULTS
= INCLUDE_DEFAULTS;         /* one target's ordering */
#else
= { ... targ_caps.gxx_include_dir ... targ_caps.tool_include_dir ... };
#endif
```

`cppdefault.cc:24` is `#include "tm.h"` — the **shared** one, i.e. the
primary's chain. So whether all 47 bases get the fully-converted per-target
table or one target's hand-built ordering is decided by the primary triple
alone. Four headers can set it
(`git grep -ln '^#define INCLUDE_DEFAULTS' -- gcc/config/` →
`linux.h netbsd.h openbsd.h rs6000/sysv4.h`), and `linux.h:122` /
`rs6000/sysv4.h:956` gate on `DEFAULT_LIBC == LIBC_MUSL`, `openbsd.h:52` on
`OPENBSD_NATIVE`. **So on a glibc-linux primary the `#else` arm is taken for
everybody and the four target orderings are unreachable; on a musl primary
linux's ordering is imposed on everybody.** Both are wrong and neither says so.

The remedy is C1-shaped and it is *not* to convert the four headers: it is that
the include *order* is a per-triple string, so `gen-target-specs-<key>` is the
program that should emit it, exactly as it emits `LINK_SPEC`. That is a real
piece of work and is scoped in §5 as item 6, not as part of the cheap fix.

### THE BRIEF'S DEADLINE CLAIM IS WRONG, AND THE TRUTH IS WORSE

The brief says the `.md` C consumers *"become hard errors once `gencondmd` goes
per back end"*. Measured, they do not, and the reason is a floor:

```
gcc/defaults.h:524-529   #ifndef HAVE_SOLARIS_AS / #define HAVE_SOLARIS_AS 0
gcc/mkconfig.sh:236-247  every `tm.h`/`tm-*.h` gets `#include "defaults.h"`
                         appended LAST, unconditionally -- no GENERATOR_FILE guard
gcc/genconditions.cc:33-36,45-47  gencondmd includes TM_H_FILE and GENCONDMD_TM_H
gcc/gen-multi-target-md.awk:1119-1120  both are `tm-<key>.h` -- PER TRIPLE
```

So `gencondmd-<key>` sees `HAVE_SOLARIS_AS 0` from `defaults.h` and compiles
clean. **`sparc.md:560` and `:8049` are not a build break; they are a silent
constant 0 in a per-triple generator — including for a Solaris triple, where
`define_insn "@tie_add<P:mode>"` (`:8049`, condition `"HAVE_SOLARIS_AS"`) is
therefore permanently disabled and the `tls_delay_slot` attribute (`:560`)
permanently takes the non-Solaris arm.**

**This is worse than the deadline it replaces, not better, and the difference
is the whole point of the project.** A build break announces itself: it names a
file, a line and a cause, and somebody fixes it that afternoon. A
permanently-unmatched `define_insn` is a back end quietly missing an
instruction pattern forever — `gencondmd` writes the condition out as `0`, the
pattern is dropped from the recognizer, and the compiler goes on emitting
correct-looking code by some other route with no diagnostic at any stage. It is
PRINCIPLES §3's "one name, several authorities, no diagnostic" in the
recognizer, and it is invisible to every instrument this branch has, because a
missing pattern produces neither an ICE nor a wrong-looking `.s` — only
different, worse code on the one target that needed it. `defaults.h:502-504` says this out loud — *"PLACEHOLDERS, not
answers ... they are 0 because nothing can supply the real value yet"* — so the
floor is honest, but it is **not** the §2a-legal supply-side kind: it is not
"upstream's own value for a back end that does not define the macro", it is
"upstream's value for the 186 triples that are not Solaris, applied to the two
that are". State that in any commit that touches it.

### THE FOUR SHAPES, AND WHY C3 IS MOST OF THE ANSWER

`defaults.h:537-541` says `HAVE_SOLARIS_LD` *"cannot become a runtime
capability in its present shape"* because its consumers are spec literals. **The
AS half is the opposite**, and nobody has said so:

| shape | sites | channel |
|---|---|---|
| already C, `if (HAVE_SOLARIS_AS && ...)` | `sparc.cc:4693`, `:4797`, `i386.cc:25715` | **C3**, a one-token change |
| selects a `targetm` hook | `sol2.h:460-462`, `i386/sol2.h:179-183`, `sparc.cc:882-885` | **C3** — move the test *inside* the hook body, the `sol2.cc:324` shape |
| selects an asm-op string | `i386/sol2.h:114-144`, `:174-177`, `:198-200`, `sparc/sol2.h:339-355` | **C3** — a function returning one of two constants, again `sol2.cc:324` |
| selects spec text | `i386/sol2.h:47-59`, `sparc/sol2.h:51-55` | **C2** — the `link_arch_gnu`/`link_arch_sun` pair |
| `.md` | `sparc.md:560`, `:8049` | **C3** — `targ_caps.solaris_as` is C, and both sites are C contexts |

`gcc/config/sol2.cc:324` is the landed template for rows 2 and 3:

```c
  return targ_caps.solaris_ld ? SOLARIS_CTORS_SECTION_ASM_OP : NULL;
```

**RULING: `solaris_as` is a `targ_caps` capability, and the probe should mirror
`solaris_ld` at `target-specs/configure.ac:2198-2206`.** It passes the
hook-vs-capability test in the capability direction without ambiguity: two
installations of the same compiler serving `sparc-sun-solaris2.11` genuinely
differ in whether `/usr/bin/as` or GNU `as` is on the path.

- The five **header** sites are pure spec text → **C1**. They are evaluated in

  already-existing `*libgcc_variants` named spec at run time, not a macro.
  **This is the half that cannot be C1**, because these TUs have no tm.h and no
  triple.

**Verdict: #69 is not blocked on design. It is two mechanical conversions on a
landed channel.**

## 6. SETTLED AFTERWARDS: BOTH `tm-<cpu>.h` AND `tm-<key>.h` EXIST, AND THE PER-BASE ONE IS THE FIRST TRIPLE'S CHAIN

Read from another agent's build dir rather than built —
`/tmp/b-a51a0e8b2b458063b-post/gcc`, configured from
`/tmp/snap-agent-a51a0e8b2b458063b-post` with 47 triples (its `config.log`
command line).

**Both headers exist, and they are generated by two different files:**

```
$ ls /tmp/b-.../gcc/tm-i386.h /tmp/b-.../gcc/tm-x86_64_pc_linux_gnu.h
-rw-r--r-- 1741 tm-i386.h                  <- per BACK END
-rw-r--r-- 1786 tm-x86_64_pc_linux_gnu.h   <- per TRIPLE

rule for the per-TRIPLE one:  multi-target-md.mk       (gen-multi-target-md.awk:1093)
rule for the per-BASE  one:   multi-target-common.mk:651 (gen-target-manifest.sh:468)
```

That second file is why the earlier grep missed it: it searched
`multi-target-md.mk` alone. Across all three generated makefiles there are
**96** distinct `tm-*.h` rule targets, not 47.

**THE 47-TRIPLE BUILD CANNOT ANSWER THE QUESTION AND MUST NOT BE QUOTED FOR
IT** — it configures exactly one triple per back end, so `cpu` and `key` are
in bijection and every discriminating case is absent. This is PRINCIPLES'
"two back ends cannot tell", in a 47-base build. What it *can* show is the
relationship:

```
$ diff tm-i386.h tm-x86_64_pc_linux_gnu.h
1,2c1,2  <  #ifndef GCC_TM_I386_H          >  #ifndef GCC_TM_X86_64_PC_LINUX_GNU_H
72c72    <  #endif /* GCC_TM_I386_H */     >  #endif /* GCC_TM_X86_64_PC_LINUX_GNU_H */
```

**Byte-identical apart from the include guard.** So the per-base header is not
a neutral or unioned thing: it is *one triple's `tm_file` chain wearing a back
end's name*, the same shape PRINCIPLES describes for the old shared `tm.h`.
`multi-target-common.mk:651` shows the chain verbatim —
`config/i386/linux64.h`, `config/glibc-stdint.h`,
`DEFINES=" ... DEFAULT_LIBC=LIBC_GLIBC ..."`, i.e. x86_64-pc-linux-gnu's.

**And the selection rule is "first triple wins", read from the generator, which
is not build-confounded** (`gen-target-manifest.sh:412-414`):

```sh
  case " ${gcc_all_cpu_bases} " in
    *" ${gcc_mt_cpu} "*) ;;                 # this back end already emitted
    *) gcc_all_cpu_bases="${gcc_all_cpu_bases} ${gcc_mt_cpu}"
       ...  printf 'tm-%s.h: ... HEADERS="%s" ...'  ${gcc_mt_incl}   # :468
```

`${gcc_mt_incl}` is *that stanza's* chain, and every later stanza sharing the
`cpu_type` takes the empty arm. So with
`--enable-targets=x86_64-pc-linux-gnu,i686-pc-cygwin`, `tm-i386.h` is linux's
chain and **`config/i386/cygming.h` never reaches the per-base axis at all.**

### WHAT THIS CHANGES ABOUT §3's `cygming.h:366` VERDICT

The verdict "a per-base channel structurally cannot give two triples of one
back end different unwind models" **stands**. But "no channel exists" was too
strong, and the correction runs *toward* the fix already landed for #208 rather
than against it. Measured:

```
gcc/target-frame.h:848-854   "Back ends whose answer really is computed -- arm,
                              c6x, ia64, i386 -- supply TARGET_EXCEPT_UNWIND_INFO
                              in their own <be>-common.cc and never reach this
                              field at all."
gcc/common/config/i386/i386-common.cc:2111-2130   i386_except_unwind_info():
    if (targ_caps.sjlj_exceptions > 0)  return UI_SJLJ;     <- PER TARGET, landed
    if (TARGET_64BIT && DEFAULT_ABI == MS_ABI && ...) return UI_SEH;
    if (DWARF2_UNWIND_INFO) return UI_DWARF2;               <- from tm-i386.h
    return UI_SJLJ;
```

So **i386 never touches `target_frame_desc.dwarf2_unwind_info`** and nothing
here contradicts #208's fix: that field serves the back ends *without* their
own hook (`target-frame.h:856-862` states its `0` is supply-side legal), and
i386 is explicitly excluded from it.

The residue is narrower and sharper than §3 said:

- The **forcing** half of `CONFIG_SJLJ_EXCEPTIONS` is already per target —
  `targ_caps.sjlj_exceptions`, read at `i386-common.cc:2120`.
- The **default** half is not. `cygming.h:362-372` encodes "32-bit
  cygwin/mingw defaults to sjlj unless `--disable-sjlj-exceptions`" by defining
  `DWARF2_UNWIND_INFO` 1 or 0; in a linux-first build that header is not in
  `tm-i386.h`, `defaults.h:418` gives `DWARF2_UNWIND_INFO 1` (i386 defines
  `INCOMING_RETURN_ADDR_RTX`), and 32-bit cygwin silently gets **UI_DWARF2**
  where upstream gives it UI_SJLJ. `cygming.h:367-368`'s own comment —
  *"The logic of this `#if` must be kept synchronised with the logic for
  selecting the `tmake_eh_file` fragment in `libgcc/config.host`"* — means the
  compiler and its libgcc would then disagree about the unwind model.

**So the open item is not "route `CONFIG_SJLJ_EXCEPTIONS` somewhere"; it is
"the per-BASE `tm-<cpu>.h` is one triple's OS layer, and every back-end fact
derived from an OS header is therefore that triple's for all its siblings".**
`DWARF2_UNWIND_INFO` is one instance; the population is every macro a
`config/<os>.h` defines that a `<be>-common.cc` or other per-base TU reads.
That is a bigger and better-defined task than #100 and it should carry the
number, with `cygming.h:366` as its worked example.
