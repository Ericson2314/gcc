## 1. THE CHOICE, AND WHY THE TRIPLE IS NOT THE BOARD'S

The task named `arm` and `arm` is what was scored.  **The triple was changed
and that is a deliberate, reported substitution**, not a silent one.

`A7D26223EEFCFA725-BOARD.md` scores `arm` as `arm-unknown-eabi` — bare metal,
no glibc.  Every existing stock control is built from
`--with-sysroot=<target glibc.dev>` plus
`--with-native-system-header-dir=/include`, and SC-BOARD.md §0 records what
happens when a control has no system headers behind GCC's `#include_next`
wrapper: **66,883 `stdint.h: No such file` diagnostics**, and a FAIL column
that agreed with the subject to 0.07% for that reason alone.  A bare-metal
control would either reproduce that floor or need a newlib recipe no other row
uses, and in both cases the row would not be comparable with the four.

So the row is `arm-unknown-linux-gnueabihf`, built on both sides from the same
materials as `aarch64`/`riscv64`/`s390x`/`x86_64`.  **It is the same `arm` back
end**; the 47 bases in the binary are unchanged.

One floor this header set carries, found before it could fire and recorded in
`-armtools.sh`: the arm glibc `.dev` has `gnu/stubs-hard.h` and **no
`gnu/stubs-soft.h`**, so a compiler defaulting to soft float dies in
`<features.h>` on every translation unit.  Measured, both sides define
`__ARM_PCS_VFP 1` and `__SIZEOF_POINTER__ 4`, so it does not fire — but it is
one `config.gcc` line away from being SC-BOARD §0 all over again.

## 4. THE TOP CAUSE, AND WHY NO BOARD OF THE FOUR COULD CONTAIN IT

`defaults.h:260` builds `ASM_OUTPUT_TYPE_DIRECTIVE` out of `TYPE_ASM_OP` and
`TYPE_OPERAND_FMT`, and `varasm.cc:6633` expands it in **shared** code, so both
are the primary's.  `elfos.h:284` is `"@%s"`; `arm/elf.h:74` is `"%%%s"`.

```
$ diff  stock.s  multi-target.s        # gcc.c-torture/compile/20010107-1.c -O0
<       .type   x, %object
>       .type   x, @object
```

**On ARM, `@` begins a comment**, so the type operand is EMPTY:

```
ccdQgx2V.s:19: Error: unrecognized symbol type ""
```

### 4a. It has been LIVE ON aarch64 THE WHOLE TIME, and could not complain

`-dissent.sh` (a `#define` sweep, anchored at line start so a mention in prose
cannot match, with `elfos.h` required as a definer or the count is declared
void) says the definers are `aarch64 arc arm elfos microblaze openbsd sparc`.
**`aarch64` asks for `%object` too** — and aarch64 is one of the four scored
targets.  So the question is not whether the four lacked a property; it is
whether they could *complain*.  `-attest.sh` assembles the offending directive
with each target's own real cross `as`:

```
TARGET                         @object    %object (control)
aarch64-unknown-linux-gnu      ACCEPTS    ACCEPTS
riscv64-unknown-linux-gnu      ACCEPTS    ACCEPTS
s390x-ibm-linux-gnu            ACCEPTS    ACCEPTS
x86_64-pc-linux-gnu            ACCEPTS    ACCEPTS
arm-unknown-linux-gnueabihf    REJECTS: unrecognized symbol type ""   ACCEPTS
```

**aarch64 has been emitting the wrong `.type` operand on every board this
project has taken**, and its assembler accepts it silently.  The `%object`
column is the control: an assembler rejecting both would mean the fragment is
malformed and neither column would mean anything.

This is PRINCIPLES' thesis in a stronger form than it states it.  It is not
only that a defect is invisible where targets *agree*; a defect can be
**present and active on a scored target** and still invisible, because that
target's tooling does not object.  No sample size on those four reaches it.

## 5. THE 32-BIT-SPECIFIC SUBSET — the honest answer

The task asks which top causes **could not have appeared on any of the four
LP64 targets**.  Measured rather than asserted, and the answer has a shape
worth stating plainly:

| cause | value | could the four have seen it? | on the pointer-width axis? |
|---|---|---|---|
| `TYPE_OPERAND_FMT` | 2,922 (89%) + most of ~21k scope | **NO** — all four assemblers accept `@object`; aarch64 carries the defect silently today | no |
| `ASM_OUTPUT_ALIGN` semantics | **0 test results** | **NO** — see below | no |
| `ilp32`/`int32plus` unevaluable | the scope difference | **NO** — a consequence of the above | **yes, as a consequence** |
| ICE `expand_one_stack_var_1` | 11 | not settled | not settled |
| ICE in LRA | 14 | not settled | not settled |

**`ASM_OUTPUT_ALIGN` is the one to read carefully, because it costs zero test
results and is wrong anyway.**  Same diff as §4:

```
<       .align  2          (stock arm)
>       .align 4           (multi-target)
```

`arm/elf.h:140` prints the **power**; `i386/att.h:59` prints `1 << LOG`, i.e.
**bytes**.  Shared code gets i386's, so a 4-byte alignment request is emitted
as `.align 4`, which arm reads as a power — **16-byte alignment**.  It
assembles cleanly into a correct-machine ELF32 object and **every test still
passes**.  `aarch64` and `riscv` also print the power, so this leak is live on
two of the four scored targets as well; `s390` prints bytes and agrees with the
primary.  A compile-only PASS/FAIL board cannot see any of it — INSTRUMENTS.md
already records that class, and this is a fresh instance, found by diffing one
`.s` rather than by scoring 171,445 results.

**So: the honest finding is that the arm row's large causes are NOT on the
pointer-width axis.**  What the row demonstrates is the more general claim of
which pointer width was only an instance: *the four agree on far more than
LP64-ness — assembler comment characters, `.align` semantics, `.type` operand
syntax — and every axis on which they agree is an axis no board of them
measures.*  A fifth target is worth what it DISSENTS about, and `arm` dissents
about things nobody had listed.

The one place the pointer-width axis does appear is derivative, and it is §4b:
the multi-target compiler is *right* that `sizeof (void *) == 4` and the
harness cannot find that out, so every `{ target ilp32 }` expectation in the
suite is evaluated against the wrong answer.

## 8. WHAT WOULD BE WORTH DOING NEXT, IN ORDER

1. **`TYPE_OPERAND_FMT` / `TYPE_ASM_OP`.**  2,922 named results plus most of
   21,181 scope, plus a live silent defect on aarch64.  Single site,
   `defaults.h:260` + `varasm.cc:6633`.  It is also the cheapest possible
   demonstration that the harness's own selectors are affected.
2. **`ASM_OUTPUT_ALIGN`.**  Zero test results and wrong on three of the five
   targets measured.  Exactly the class that needs a both-sided `.s` diff
   rather than a board, so it should land together with a sweep for the rest
   of that class (`ASM_OUTPUT_SKIP` is in the same diff: `.zero` where arm
   says `.space`).
3. **The two ICE families**, 25 results, reproducers in §3, neither attributed.
   `expand_one_stack_var_1` is `gcc_assert (byte_align * BITS_PER_UNIT <=
   MAX_SUPPORTED_STACK_ALIGNMENT)` on a 16-byte vector local; stock arm
   compiles the same file.
4. **A `-fouragree.sh`-shaped instrument that reads STOCK per target.**  The
   version committed here asks the MULTI-TARGET compiler and therefore returns
   a uniform table by construction — it is measuring the symptom, not the
   population.  That is recorded in its own header rather than quietly fixed,
   because the next person will reach for exactly that shape.
