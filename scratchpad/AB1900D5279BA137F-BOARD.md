**The riscv64 twenty are a compiler defect wearing the KILLED column's
clothes, and the scorer cannot tell.** Every one of them reads

```
riscv64-unknown-linux-gnu-as: out of memory allocating 9223372036854841454
  bytes after a total of 270336 bytes
```

on `gcc.c-torture/execute/align-2.c` and `align-3.c`. 9223372036854841454 is
2^63 − 6162: the compiler emitted an alignment/size directive with a nonsense
operand and the assembler tried to honour it. That is a leaked-answer bug on
an alignment computation, not machine load, and netting it out of the board as
"contamination" would delete the only signal it produces. It is left in the
KILLED column because that is where the harness puts it, and flagged here
because the column's own name is wrong for these twenty.

### HOW EACH CAUSE BELOW IS SIZED, AND THE ARITHMETIC I GOT WRONG FIRST

An ICE's count and a share of the debt are **two different numbers**, and the
obvious way of relating them returns zero. A DejaGnu test name carries the
diagnostic:

```
FAIL: gcc.dg/foo.c  -O2  (internal compiler error: in ..., at regs.h:312)
FAIL: gcc.dg/foo.c  -O2  (test for excess errors)
```

Stock produces **neither** line — it passes — so when the runs are joined by
(name, occurrence) the ICE-annotated row has no counterpart and lands in
ONLY-IN-MULTI-TARGET. The row that joins, and therefore the row that *is* the
debt, is the `(test for excess errors)` sibling, whose text names no
diagnostic. **`grep in_hard_reg_set_p` over x86_64's debt returns 0** on the
target where that ICE is dominant — a zero from a correct-looking pipeline, in
the direction that says the cause does not matter. I wrote "one cause is 59%
of the debt" off exactly that arithmetic before checking it, and it was wrong
in both directions at once.

The sound question is at the FILE level and `mt-debt-attribute.sh` asks it:
how many debt results belong to test files that hit the diagnostic anywhere.
**That is an UPPER BOUND** — a file that ICEs at `-O2` may owe some of its debt
to something else — and no lower bound is derivable from a `.sum` at all;
getting one means re-running those files with the cause fixed.


overwhelmingly SCOPE, not quality, and the honest statements about riscv64 are
the name-based ones: 10,676 tests genuinely got better and 71 genuinely got
worse. Anyone quoting riscv64's PASS column against the previous board without
this number is quoting the cardinality effect.
