# #208 — aarch64 emitted NO DWARF CFI at all

Snapshot `807cf0703bc` (fix) against `cad1a29fbdc` (before), anchor **52** on
both, cold builds from immutable snapshots, build dirs
`/tmp/b-a62563d5673423af6-{2b,2c,47}`.

## One predicate, two symptoms, and the direction is not what the brief guessed

`targetm_common->except_unwind_info (&global_options)` answered **UI_SJLJ** for
aarch64. Both reported symptoms read that value *independently*:

```
dwarf2cfi.cc:3723   dwarf2out_do_eh_frame   == UI_DWARF2  -> emit CFI
opts.cc:1564        diagnose_options        == UI_SJLJ    -> kill
                                              -freorder-blocks-and-partition
```

The brief proposed that "no CFI" might *explain* the silent disable. It does
not: `opts.cc:1564` never consults CFI state. They are **siblings of one
cause**, and that was settled by reading the two call sites rather than by
either symptom moving.

A **third symptom nobody had reported** falls out of the same read:
`c-cppbuiltin.cc:1221` predefines `__USING_SJLJ_EXCEPTIONS__` on the SJLJ
branch, so aarch64 was advertising SJLJ exceptions to every translation unit.

## Cause

`953cf9eda76` ("tm.h removal: 58 shared TUs, each REBUILT without the line")
deleted `#include "tm.h"` from `common/common-targhooks.cc`. That file reads

```c
#ifdef DWARF2_UNWIND_INFO
  if (DWARF2_UNWIND_INFO)
    return UI_DWARF2;
#endif
  return UI_SJLJ;
```

so the `#ifdef` silently became FALSE and every back end without its own
`TARGET_EXCEPT_UNWIND_INFO` began answering UI_SJLJ. i386 supplies one
(`i386-common.cc:2133`), which is exactly why x86_64 was unaffected and has
been a valid control throughout.

**The removing sweep had a guard for this class and it could not have fired.**
It required the TU to have genuinely lost `tm.h` (`GCC_TM_H` undefined under
`-E -dM`). That asks whether the amputation HAPPENED, not whether a
conditional CHANGED SIDES. Same geometry as PRINCIPLES §7's three
cleared-hypothesis rows: a check answering a different question than the one
being settled, whose clean result reads as confirmation.

**Restoring the include would not have been the fix.** Before the removal this
file read i386's `DWARF2_UNWIND_INFO` for all 47 back ends — the leak this
project exists to remove, which merely happened to give aarch64 the right
answer. That is why the *removal* reads as the regression and the *leak* does
not.

## Why `common-targhooks.cc` was uniquely broken — the other two readers are fine

Measured, because "one file lost it, so the family is broken" was the natural
next claim and it is false here:

```
builtins.cc:8485          #ifdef DWARF2_UNWIND_INFO   still TRUE (transitively)
c-family/c-cppbuiltin.cc:1680                         still TRUE (transitively)
common/common-targhooks.cc:41                         FALSE   <- the bug
```

Both survivors were checked by observable, not by grep:
`__GCC_HAVE_DWARF2_CFI_ASM` is predefined on x86_64 AND aarch64, and
`__builtin_init_dwarf_reg_size_table` still expands to a real table (aarch64:
8 bytes per register, its own answer) rather than falling out of the switch.
`common-targhooks.cc` is the one that breaks because it lives in
`libcommon-target.a` and includes almost nothing.

**Both survivors are still latent leaks and are NOT fixed here.** They read
i386's value, which is 1, so the guard is "on" for everyone; a back end that
genuinely has no DWARF unwind would wrongly get those builtins. Reported, not
netted out.

## The fix

A real per-base answer, in the family that already owns the question.
`DWARF2_UNWIND_INFO` is `defaults.h:418`'s derivation from "does this base
define `INCOMING_RETURN_ADDR_RTX`", which #194 already made a per-base fact on
`target_frame_desc`. This was the member still missing, beside #125's
`dwarf_frame_regnum` / `dwarf_frame_return_column`.

```
target-frame.h            new  int (*dwarf2_unwind_info) (void)
target-cumargs.cc         mt_base_dwarf2_unwind_info -- reads the macro in
                          THIS base's TU, via BASE_HEADER (tm.h)
target-cumargs-select.cc  mt_dwarf2_unwind_info () off mt_frame ()
common-targhooks.{h,cc}   mt_dwarf2_unwind_info_hook, read instead of #ifdef
multi-target-select.cc    stores the hook beside targetm_frame
```

**The archive boundary is why it is a pointer.** The consumer is in
`libcommon-target.a`, which `xgcc`, `cpp` and `lto-wrapper` link WITHOUT
`libbackend.a`; a direct call is an undefined symbol in three programs. Null
in a driver, and null is **fatal, not a default** — "nobody installed an
answer" and "this target has no DWARF unwind" are different facts, and letting
them share the UI_SJLJ return is what made this invisible.

Checked, not assumed: `cc1` with no `-ftarget-config` still dies on the
pre-existing *"no target configuration was selected"* diagnostic, so the new
fatal preempts nothing.

## Evidence

Both-sided, and the pre-fix compiler survives in `/tmp/b-a62563d5673423af6-2b`
so the A/B is against a real binary, not a memory (`cc1` md5 `47172ce1be22`
vs `beddb779796a`, asserted different before comparing).

```
                     BEFORE (2b)                     AFTER (2c / 47)
aarch64  hook        SJLJ                            DWARF2
         __USING_SJLJ_EXCEPTIONS__  1                0
         rbp note    present                         absent
         .cfi_startproc/def_cfa/offset  0 / 0 / 0    1 / 4 / 9
x86_64   hook        DWARF2                          DWARF2   (unchanged)
         .cfi_startproc/def_cfa/offset  1 / 4 / 3    1 / 4 / 3
```

Non-vacuity on every zero above: the probe function's body is present in the
`.s` in all cases (4 `mt_cfi_probe` lines), so `0` means *no CFI*, not *no
code*. The probe is deliberately **non-leaf** — a leaf needs no CFI, so an
empty and an absent stream are indistinguishable on one.

**Object level, aarch64's own `as` and `readelf`** (real cross binutils, not a
shim), at 47 bases:

```
main     .eh_frame=80  CIE=1  FDE=1  DW_CFA_def_cfa=5
control  .eh_frame=0   CIE=0  FDE=0  DW_CFA_def_cfa=0
```

and the frame is **semantically aarch64**, which is the arm PRINCIPLES asks
for after riscv64 passed "assembles, right ELF machine" while emitting 32-bit
code:

```
Return address column: 30            <- x30/LR, aarch64's own answer
Code alignment factor: 4             <- aarch64 instruction size
DW_CFA_def_cfa: r31 (sp) ofs 0
DW_CFA_offset: r29 (x29) at cfa-48
DW_CFA_offset: r30 (x30) at cfa-40
```

Return-address column **30** is the end-to-end confirmation that #194's
`INCOMING_RETURN_ADDR_RTX` conversion is working: i386's answer would have
built a CIE claiming the return address was already in memory.

**The negative control was broken on first run and the correction is the
useful part.** `-fno-exceptions -fno-asynchronous-unwind-tables` still leaves
`flag_unwind_tables` set, because aarch64's `unwind_tables_default` is true —
so the "control" produced exactly as many FDEs as the main arm and the script
reported FAIL on a tree where the fix was working. A control that cannot go
quiet is the null-result-as-a-pass shape. `-fno-unwind-tables` is required.

**Not aarch64-specific.** riscv64 and s390x also move to DWARF2 and emit CFI
(`startproc=1 def_cfa=4 offset=6` and `def_cfa=3 offset=7`). Their objects
still fail at the assembler for **pre-existing, unrelated** defects — riscv's
empty `.attribute arch` (the shape PRINCIPLES already records) and an s390
displacement out of range — which this change neither causes nor fixes.

## `maybe_record_trace_start`: GONE, and NOT by this change

The honest answer the brief asked for.

```
gcc.dg, aarch64, 47-base tree, compile-only, real cross binutils
  maybe_record_trace_start                0        (was 7)
  remaining aarch64 ICE sites: hashtab_chk_error 21, final_scan_insn_1 3,
                               assert_rtx_eq_at 3
```

Both named reproducers (`gcc.dg/shrink-wrap-sibcall.c`, `gcc.dg/pr59418.c`) at
`-O2 -g` are clean on **both** compilers — i.e. they were already clean
*before* this fix. #194's `INCOMING_RETURN_ADDR_RTX` conversion closed them;
this task did not, and a one-sided run would have let it bank that result.

`-g` matters and is not decoration here: `dwarf2out_do_frame` returns true for
`dwarf_debuginfo_p ()` regardless of the unwind method, so the CFI pass runs
at `-g` even when the hook says UI_SJLJ. The #208 bug therefore neither caused
nor masked these ICEs.

Also gone since it was recorded: the x86_64 `cselib.cc:2650` ICE on
`shrink-wrap-sibcall.c` (rc=0 now on both compilers).

## What is NOT claimed

- **The `-freorder-blocks-and-partition` re-enable is measured by the absence
  of the note, not by a partitioned binary.** `opts.cc` no longer takes the
  branch and no longer informs; that the optimisation then does useful work on
  aarch64 is untested.
- **The ICE tally is `dg.exp` only**, on a run with **2 KILLED** (memory
  exhaustion, machine contamination) and load 11–15 at scoring time. Both
  named reproducers live in `gcc.dg`, so the comparison is valid for that
  cause; a whole-suite figure is not claimed.
- **`builtins.cc` and `c-cppbuiltin.cc` still read i386's
  `DWARF2_UNWIND_INFO`.** Measured harmless today; left as a named follow-up.
- The 47-base run covers `all-gcc`, not the testsuite at 47 targets.
